# Changelog

All notable changes to HostPanel are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed

- SSH key agent 1.4.0: a new `remove-jail` operation removes the SSH jail and its home mount unit of an account the hosting panel has already deleted (it refuses while the account exists and while anything is still mounted inside the jail, and removes the tree on its own filesystem only). HostPanel asks for it after it terminated a service's hosting account. Before, every terminated jailed account left its jail and an enabled systemd mount unit on the server, because the agent keeps a jail for cheap re-enrolment.

### Fixed

- SSH key agent 1.3.1: the CWP `prepare-site` helper sets `HOME=/root`. The agent runs helpers with `PATH` only, so `mysql` could not read root's client credentials and every site preparation through the agent failed with `site_prepare_failed`, while the same helper worked when run by hand.

### Added

- SSH key agent 1.3.0: an opt-in `prepare-site` operation (`site_prepare_command` in `agent.conf`, empty by default) runs a provider helper as root that prepares one account's own domain for Innovayse Sites deploys. The CWP helper (`providers/cwp/prepare-site`) sets up a php-fpm 8.3 pool with the OPcache and realpath settings a symlink-switch deploy needs behind Apache, the vhost handler and CWP's own record of it, a database, the deploy settings file, `public_html -> current/public` and PHP in the jail. It is idempotent, backs up what it edits, refuses a domain that is not the account's (`site_not_owned`) and reloads Apache and php-fpm only gracefully and after their config tests.
- A hosting product whose metadata holds `{"innovayseSites": {"prepare": true}}` has every newly provisioned account prepared that way through the server's agent, in the background after provisioning. Failures are logged and leave the service active.

### Fixed

- The **Hidden** switch of a product now takes effect. It was never sent, and the product API had no way to change the status, so a product created or edited with it on was saved active and stayed on the order form and in the public catalogue. Turning it on sets the product inactive (off the order form and `GET /api/public/products`), turning it off sets it active again, on both create and edit. The create and update calls take `isHidden`; an update that leaves it out keeps the stored status.

## [0.5.0] - 2026-11-13

Highlights since 0.4.0:

- Payment plugins can answer a form post or a browser step, and a plugin can serve its checkout page from a public callback. This needs plugin SDK 3.7.0.
- A client can save the payment method within the checkout payment, pay by manual bank transfer, top up a wallet balance and receive credit notes.
- Billing gained tax rules with automatic tax on new invoices, plan upgrades and downgrades with proration, and an Upcoming Renewals page.
- Product bundles, fraud detection with a review queue, and email campaigns with segments, one click unsubscribe and open and click tracking.
- Plugins: restricted registry plugins and managing registry plugins from the admin panel.
- The installer backs up the database before an upgrade and can roll it back.

Upgrade notes, read before upgrading:

- The ticket status Answered is gone. A data migration turns existing Answered tickets into Awaiting Reply.
- The HTTP clients the host hands to a plugin no longer follow redirects, as plugin SDK 3.7.0 requires. A plugin that relied on a followed redirect must handle the 3xx reply itself.
- With single sign-on, register the API as the back-channel logout receiver (`/api/auth/backchannel-logout`) for this client, otherwise an admin session outlives a sign-out everywhere (details below).

### Removed

- Support: the ticket status Answered is gone. A ticket is Open, Awaiting Reply or Closed. Existing Answered tickets become Awaiting Reply in a data migration, the Customer-Reply filter of the admin ticket list is removed, and the old Answered filter is now named Awaiting Reply. Importing tickets from another system is unchanged.

### Added

- Payments: a payment plugin can now answer a form post or a browser step (#1174, plugin SDK 3.7.0). The portal submits a form post as a form it builds itself from the plugin's fields, and sends the payer to the page of a browser step. When the payer comes back, the result page hands the parameters of the return request to the plugin (`IPaymentReturnPlugin`, capability `paymentReturn`), within the limits of the SDK, and only then reads the payment status. A form that breaks the SDK's rules, or a browser step from a plugin that cannot complete a return, is a failed payment and the order it registered is cancelled.
- Plugins: a public callback can answer an HTML page, so a gateway can serve its checkout page. The page is sent under a strict content security policy that allows only the https origins the plugin lists in `externalOrigins`, runs sandboxed, is never cached and sends no referrer.
- Plugins: the Browse tab of the admin Plugins page shows three cards per row on wide screens, two on medium ones and one on narrow ones, in the layout of the public plugin list, and each card shows the rating (stars, average and number of reviews) when the registry sends one (#1168).
- Payments: a client can save the payment method within the payment of the checkout (#915). The portal offers the choice only in the checkout payment, not on the payment page of an existing invoice, although the start requests of the invoice payment and of the order payment both accept it. Checkout lists a payment plugin that offers stored credentials with `supportsStoredCredentials` set to true, and the start requests take `savePaymentMethod` and the `consentTextVersion` the client ticked. The host makes sure the gateway customer exists, registers the payment with `PaymentInstruction.SavePaymentMethod`, and records the consent in the same save that records the session, with the wording version and the address and browser of the request. Only the signed in owner of the invoice can ask for it, and a user linked to the account only with the permission to view and pay invoices (`CLIENT_PERMISSION_DENIED` otherwise, while paying without saving stays allowed); a guest pays as before. A payment that saves is also refused when card processing is disabled for the client. When the payment is paid, the method the plugin reports in `GatewayPaymentStatus.SavedMethod` is bound to that consent in the save that settles the invoice, by the return page and by the reconciliation job alike, and it then lists among the saved methods, with its brand and last four digits when the plugin lists it for the customer. A missing, revoked, conflicting or too long method reference never fails the payment. This needs SDK 3.5.0. The public demo gateway reports a demo card for a payment that saves, but a payment request names no customer, so the demo does not add that card to the customer's list and the saved method shows without brand and last four digits. The save session and the payment now share one place that creates the gateway customer and one that binds a method to its consent.
- Product bundles (#80), the backend part. An admin groups products into a bundle with one primary product, an optional included domain registration (1 to 10 years, priced per extension when the order is placed) and a percentage or fixed discount. Bundles are managed under `/api/products/bundles` and the active ones are listed for the storefront at `GET /api/public/product-bundles`. The orders table gains a nullable `BundleId` for the next part, which places an order from a bundle.
- Billing: tax rules screens (#65), the interface part. Staff get **Settings, Tax Rules**, a list of tax rules with Add, Edit and Delete: each rule has a name, a country picked from the country list, an optional region, a rate in percent and an enabled switch, and a refusal such as a second rule for the same country and region is shown inside the dialog. The client profile and the Add Client form have a **Tax ID** and a **Tax Exemption Reason** next to the Tax Exempt switch. The setting `billing.tax.enabled` shows in the System Settings list like the other billing settings. Texts are in English, Russian and Armenian.

- Billing: tax rules and automatic tax on new invoices (#65), the backend part. Staff manage tax rules per country and optionally per region (state) with `GET`, `POST`, `PUT` and `DELETE /api/admin/tax-rules`: each rule has a name, an ISO country code, an optional region, a rate in percent (0 to 100, up to three decimals) and an enabled switch, and there is at most one rule per country and region (`TAX_RULE_ALREADY_EXISTS`, `TAX_RULE_NOT_FOUND`, `TAX_RULE_RATE_INVALID`). A new invoice is taxed at the rate of the client's country: the enabled rule of the client's region first, then the enabled country-wide rule, and nothing when there is none. The rate is fixed on the invoice when it is raised, so changing or deleting a rule later does not change an issued invoice. This applies to order invoices, renewal invoices, invoices for billable items, invoices converted from a quote and invoices created by staff; credit top-up invoices stay untaxed. The new setting `billing.tax.enabled` (on by default) switches automatic tax off for everyone. A client now has a **tax id** and a **tax exemption reason** (`taxId` and `taxExemptionReason` in the client settings, the client export and the client brief); a tax exempt client is never taxed. The new table is `TaxRules` and the migration adds two columns to `Clients`. Tax per line item, VAT number validation and tax included pricing are not part of this change.
- Fraud detection (#74), the backend part. Registrations and orders are scored from 0 to 100 before anything is created, with no external service needed: an IP address or CIDR range, an e-mail domain or a country on the block list is a strong signal, a disposable mailbox domain, several accounts from one IP address (`fraud.max_accounts_per_ip`), too many orders from one IP address within a window (`fraud.velocity_max_orders` within `fraud.velocity_window_minutes`) and a billing country that differs from the country of the IP address (known when the MaxMind integration answers) add to the score, and the sum is held to 100. A score below `fraud.manual_review_risk_score` (50 by default) goes through; from it up to `fraud.auto_reject_risk_score` (90 by default) the order is placed and held in the new status `UnderReview`, with its score and reasons, and a payment for it fulfils nothing; from the reject score the order is refused with `ORDER_FRAUD_REJECTED` and a registration with `REGISTRATION_FRAUD_REJECTED`, and nothing is created. A registration that only scores into the review band goes through and is logged. When the MaxMind integration is set up and switched on, minFraud Insights is asked as well (the address, the e-mail domain and the billing country only) and the higher of the two scores counts; a failure of the service is logged and the local score decides. Every decision is written to the fraud log. Staff work through: `GET /api/orders?status=UnderReview` (the review queue, each row with `ipAddress`, `fraudScore` and `fraudReasons`), `GET /api/orders/{id}`, `POST /api/orders/{id}/approve-review` (back to Pending, fulfilled at once when its invoice was already paid) and `POST /api/orders/{id}/reject-review` with a reason (the order becomes Fraud, its open invoice is cancelled and the client is mailed the reason with the new `order-rejected` template); `GET` and `PUT /api/admin/fraud/settings`; `GET`, `POST` and `DELETE /api/admin/fraud/blocklist`; `GET /api/admin/fraud/log` filtered by decision and reason. Fraud detection is off until `fraud.enabled` is turned on. The new tables are `BlockListEntries` and `FraudLogEntries`, and `Orders` gains `FraudScore` and `FraudReasonCodes`. New error codes with sentences in English, Russian and Armenian: `ORDER_NOT_UNDER_REVIEW`, `ORDER_FRAUD_REJECTED`, `REGISTRATION_FRAUD_REJECTED`, `FRAUD_BLOCKLIST_VALUE_INVALID`, `FRAUD_BLOCKLIST_ENTRY_EXISTS` and `FRAUD_BLOCKLIST_ENTRY_NOT_FOUND`.

- Product bundles (#80), ordering and screens. A client orders a bundle from the new **Bundles** page of the storefront: the bundle fills the cart with its products, each on the billing cycle the client picks, and when the bundle includes a domain the client searches for it and registers or transfers it for the years the bundle fixes. `POST /api/orders` takes an optional `bundleId` next to the usual `items`. The server accepts only the bundle's own product lines and one domain line when the bundle includes a domain (a renewal is refused), sets the domain years to the bundle's, takes the client group discount as for any order, and then takes the bundle discount off those prices: a percentage off every line, or a fixed amount, converted to the client's currency when it is stated in another, spread over the lines in proportion to their prices with cumulative rounding, so the line discounts add up exactly to the total, and never more than the subtotal. A fixed discount in a currency that is not stored is refused before anything is created. Tax is worked out on the discounted line, the order remembers its bundle, and every invoice line ends with the bundle's name. New error codes with sentences in English, Russian and Armenian: `PRODUCT_BUNDLE_NOT_AVAILABLE`, `ORDER_BUNDLE_ITEMS_MISMATCH`, `ORDER_BUNDLE_DOMAIN_MISMATCH`, `ORDER_BUNDLE_DOMAIN_ACTION_NOT_ALLOWED` and `ORDER_BUNDLE_DISCOUNT_CURRENCY_UNAVAILABLE`. Staff manage bundles on the new **Product Bundles** screen of the admin panel, and an order placed from a bundle shows the bundle on its detail page. The staff guide describes bundles in English, Russian and Armenian. This closes #80.

- Services: plan change screens (#79), the interface part. A client opens the new **Change Plan** tab of a service, sees the other plans of the product group with the prorated amount of each, and submits a change; the page then shows whether the plan changed at once, waits for payment of the upgrade invoice (with a link to pay it) or waits for staff to approve a downgrade. Staff get **Clients, Plan Changes**, a list of plan change requests filtered by status, with Approve and Reject (an optional note) for each pending request, and a plan change history link on the service page of a client. The setting `billing.plan_change.auto_approve_downgrades` decides whether a downgrade is approved without staff, and the credit it gives is shown as `PlanChangeCredit` in the client's credit history. Texts are in English, Russian and Armenian.
- Currencies: the exchange rates are now refreshed by themselves every day at 03:00 UTC (#66), with the same update as the admin panel button, so a currency the source does not quote keeps its rate. A source that cannot be reached, or an installation with no base currency yet, leaves the rates as they were and the job tries again the next day; it never stops the job. The hour is `ScheduledJobs:UpdateExchangeRatesHour` and an installation with no outbound internet access turns the update off with `ScheduledJobs:DisableExchangeRateUpdates` (`DISABLE_EXCHANGE_RATE_UPDATES` in the compose files). The product prices are still not recalculated by this job; that stays the operator's decision.

- Services: plan upgrade and downgrade with proration billing (#79), the backend part. A client moves an active service to another active product of the same product group with `POST /api/me/services/{id}/plan-change` after reading the plans, each with its type and prorated amount, from `GET /api/me/services/{id}/plan-change-options`. The amount is the difference of the two recurring prices for the share of the current billing cycle that is left (a started day counts as a whole day, a renewal date already passed counts as nothing), rounded to the minor units of the client's billing currency. An upgrade is approved at once and raises an invoice for the prorated charge; the plan changes when that invoice is paid (an upgrade with nothing left to prorate changes at once). A downgrade credits the prorated amount to the client's balance (the new credit movement `PlanChangeCredit`), at once when the new billing setting `billing.plan_change.auto_approve_downgrades` is on (off by default) and otherwise after staff approve it. Staff list the requests (the pending queue or one service's history) with `GET /api/admin/service-change-requests`, and approve or reject them with `POST /api/admin/service-change-requests/{id}/approve` and `/reject`; approving a request the hosting panel refused repeats it, and rejecting an upgrade cancels its unpaid invoice. Every approval ends in one use case that asks the hosting panel for the new package of a provisioned service first, so a refusal changes nothing and credits nothing. The new table is `ServiceChangeRequests`. New error codes with sentences in English, Russian and Armenian: `SERVICE_CHANGE_REQUEST_NOT_FOUND`, `SERVICE_CHANGE_ALREADY_PENDING`, `SERVICE_CHANGE_SAME_PRODUCT`, `SERVICE_CHANGE_SAME_PRICE`, `SERVICE_CHANGE_PRODUCT_NOT_AVAILABLE`, `SERVICE_CHANGE_PRICE_UNAVAILABLE`, `SERVICE_CHANGE_NO_RENEWAL_DATE`, `SERVICE_CHANGE_INVOICE_UNPAID` and `SERVICE_CHANGE_INVALID_STATE`.

- Email campaigns (#83): an admin writes a marketing email, picks who gets it with segments (every active client, owners of a product, clients in a country, or clients with a service that renews within a number of days), sees how many clients that reaches, previews the mail, and sends it now or at a chosen time. Only active clients who agreed to marketing email are mailed. Each mail carries a personal unsubscribe link that withdraws the client's consent, and the campaign shows how many mails were sent, failed or unsubscribed. The `DispatchEmailCampaignsCron` job starts due campaigns and sends them in batches through the `email-campaign` mail template (`ScheduledJobs:DispatchEmailCampaignsIntervalSeconds`, 30 seconds by default). The `campaigns.send_rate_per_minute` system setting (60 by default, from 1 to 600) caps how many campaign mails go out in any one minute over all campaigns, and the mails above the limit wait for the next pass.

- Email campaigns: two more segment types (#83). A segment can pick the clients of one client group, or the clients who have not signed in for a number of days. The sign-in segment counts only clients whose record is at least that many days old (a client imported with an old sign-in but a new record is left out), and only where the panel owns its accounts: with an external sign-on provider the last sign-in is not known, so the segment is refused with a validation error and the admin form does not offer it. The admin segment row shows a group picker or a days field for them.

- Email campaigns: one click unsubscribe (#1070). Campaign mails now carry `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, and the `List-Unsubscribe` address points at the public API route `POST /api/public/unsubscribe/one-click?token=TOKEN`, which needs no portal CSRF header, uses the global rate limit and not the strict one, because mail providers post the one click requests of all their users from a few shared addresses, and checks only the token hash. The unsubscribe page endpoint `POST /api/public/unsubscribe` keeps the strict rate limit. The unsubscribe page in the client portal now waits for a confirm button and sends a no referrer policy (#1072).

- Email campaigns: open and click tracking (#83). Every campaign mail ends with a one pixel image and its web links go through the panel, so a campaign shows how many mails were opened and how many links were clicked, each as a total and as the number of readers, and the open rate and click rate over the delivered mails. A link leads only to an http or https address written in the campaign body: the address is read from the stored body by the position of the link and never from the request, and mail, phone, script and relative links are left as written. The pixel and the links carry a tracking token of their own, kept only as a hash and separate from the unsubscribe token, so an address seen in a proxy log cannot unsubscribe the reader. The new public routes `GET /api/public/campaign-mail/open/{token}` and `GET /api/public/campaign-mail/click/{token}/{index}` use the global rate limit and not the strict one, because image proxies of large mail providers fetch from few addresses. The recipient table gains the columns `TrackingTokenHash` (unique), `OpenCount`, `FirstOpenedAt`, `ClickCount` and `FirstClickedAt`, and the campaign stats and the admin stat tiles show the new figures. Opens are an upper bound, because some mail clients load images without the reader opening the mail, and clicks may be too, because link scanners in mail security tools follow every link in a mail. The open and click rates count only readers of delivered mails, so they cannot pass 100 percent. The tracking token in the path of these routes is masked in the API request log, and the bundled nginx edge masks it, and the unsubscribe token in a query, in its access log. A Caddy edge writes no access log unless an operator turns it on, and an operator's own proxy in front must mask these paths itself. The new error code `CAMPAIGN_MAIL_LINK_NOT_FOUND` has sentences in English, Russian and Armenian.

- Knowledge base: articles belong to a category by id, have a slug, and are written per language (#538). The category of an article was free text, so `Hello` and `hello` were two categories and a category could not be deleted safely; it is now a foreign key, and a category that still holds articles is refused with `KBCATEGORY_IN_USE`. Articles and categories get a unique slug (lower case, never numeric, not the words `articles` or `categories` for an article) built from the English title or the name, fixed once created; the public `GET /api/knowledgebase/{id}` also answers `GET /api/knowledgebase/{slug}`, matched without regard to case, and the public list, search and category routes keep their shape and add `slug` and `categorySlug`. The title and body move to a per language translation table like the FAQ: English is required, a reader gets their language, else the default one, else the first the article has, and the search looks into every language. The migration merges category spellings that differ by case or edge spaces, gives every article a slug that cannot clash, and keeps each existing text as one translation in the language its own letters show (Armenian `hy`, Cyrillic `ru`, otherwise `en`); rolling it back is not exact: the other languages, the slugs and the original spelling of a merged category are lost. The admin panel writes an article in three language tabs, lists the articles and edits them. The admin API takes `categoryId` and `translations` instead of `title`, `content` and `category`.

- Plugins: restricted registry plugins (#1022). A plugin the registry marks as host only is given only to an installation the registry has verified. Hostpanel generates an Ed25519 key pair once (the private key is stored encrypted in the settings and never sent), registers the public key and the public address (`ClientBaseUrl`) with the registry, serves the registry's challenge at `GET /.well-known/hostpanel-registry/{id}` (anonymous, `text/plain`, `Cache-Control: no-store`), and asks the registry to verify it. Registration runs by itself, in a background job at start and when a restricted plugin is asked for, is safe to repeat, and backs off from 30 seconds to one hour after a failure. For a restricted plugin the version list, the release details, the download ticket and the package fetch carry `X-Hostpanel-Instance`, `X-Hostpanel-Timestamp`, `X-Hostpanel-Nonce` and `X-Hostpanel-Signature` and no licence key; the package is fetched against a one time ticket. The unsigned newest-version lookup may answer an empty package address for a restricted plugin. New error codes with sentences in English, Russian and Armenian: `PLUGIN_REGISTRY_INSTANCE_ADDRESS_INVALID`, `_NOT_VERIFIED`, `_REVOKED`, `_CHALLENGE_UNREACHABLE`, `_SIGNATURE_REJECTED`, `_CLOCK_SKEW` (fix the server clock), `_REPLAY_REJECTED`, `_LIMIT_REACHED` and `PLUGIN_REGISTRY_DOWNLOAD_TICKET_REFUSED`. New endpoints `GET /api/admin/plugins/registry-instance` and `POST /api/admin/plugins/registry-instance/retry`, and a Registration card on the Browse tab with the state (not registered, waiting, verified, revoked, failed) and a Retry button. The edge proxy must send `/.well-known/hostpanel-registry/` to the API; the Docker Hub Caddyfile and the nginx template do. No database migration: the identity is one encrypted settings row.

- Orders: a failed order line can be retried (#537). Every line now keeps its own fulfilment state (Pending, InProgress, Fulfilled, Failed, Refunding, PartiallyRefunded or Refunded), the code the last failed attempt ended with, the number of attempts and the time of the last one. An accepted order with a failed line is no longer shown as Active but as the new status Incomplete, and returns to Active when no line is left open; the order list shows how many lines need attention and can be filtered by Incomplete, which is the list of orders whose lines were forgotten. Staff retry one line with `POST /api/orders/{id}/items/{itemId}/retry` or the Retry button on the order page: the same fulfilment runs again, a line that is already fulfilled is refused with `ORDER_LINE_ALREADY_FULFILLED`, and two retries of the same line cannot both run (`ORDER_LINE_NOT_RETRYABLE`). A retry never repeats what the first attempt already did: a service is stored with the order line it was created for (one service per line), so a retry after a failed activation or a run that died reuses that service instead of ordering a second one that would be provisioned and billed twice; a domain the client already holds under that name, active or pending, is counted as done (an expired, cancelled or transferred out one is not); and a renewal the same line already sent to the registrar is stored with the domain and is not sent again. A registrar timeout or any other unexpected error in one line now fails only that line with `HOSTPANEL_UNEXPECTED`: the lines already finished stay recorded (each outcome is saved the moment it is known), the lines after it still run, and the failed line is retryable at once; such a line is not refunded automatically because the registrar may have registered the domain. A cancelled run records the lines it did not finish as failed with `ORDER_LINE_INTERRUPTED` before it rethrows. The order's status is worked out from the lines as they are saved, so two retries of different lines finishing together cannot leave an order Incomplete over lines that are all fulfilled, and a save that loses a race is answered with `ORDER_LINE_CHANGED` (409) instead of a 500. When a rejected domain line is refunded, the line is first claimed as Refunding, which no retry can take, so a line is never both refunded and delivered; it then ends Refunded when everything came back, Failed again when nothing did, or PartiallyRefunded (closed to retries, order stays Incomplete) when only part came back and staff must finish the refund by hand (`ORDER_LINE_NOT_REFUNDABLE` when a refund step is asked of a line in the wrong state). How long a retry's claim holds a line is the new setting `Orders__RetryLeaseMinutes` (default 10, 1 to 1440). Each retry is written to the client's activity log. Every line is claimed (in progress, its attempt counted) in the same save that accepts the order, so a crash leaves the lines claimed and the order Incomplete, retryable once the claim runs out, instead of lines that read as never started on an Active order; an outcome that cannot be recorded no longer stops the other lines, and every outcome carries the attempt number of its claim, so a late outcome of an attempt whose claim was taken over is refused with `ORDER_LINE_CHANGED` and never overwrites the newer result. A retry cancelled after its claim records the line as `ORDER_LINE_INTERRUPTED`. A registration or transfer is counted as done on a retry only when the domain was created by the same order (the domain stores its order), and the renewals an order line made are kept in their own table (`DomainLineRenewals`), so a renewal made another way can no longer make the line renew twice. Two attempts of one line creating its service at once get the same service instead of a database error, and a service stored for a line that belongs to another client or product is refused with `ORDER_LINE_SERVICE_CONFLICT`. A partly refunded line can be closed as refunded after staff finished the refund by hand, with `POST /api/orders/{id}/items/{itemId}/close-refund` or the Refund finished button on the order page (audited). The migrations add four columns to `OrderItems`, `ClientServices.OrderItemId` with a unique index where it is set, and the `DomainLineRenewals` table. Lines that were accepted before the migration read as Pending, their orders stay Active, and those lines cannot be retried: a retry is only offered for a failed line of an Incomplete order, so a line that was never fulfilled before this release has to be fixed by hand.

- Reports: the VAT MOSS report now takes account credit notes off the quarter (#1011). A credit note given as account credit reduces the net value and the VAT of its country, rate and currency in the quarter it was issued in, the date of the correction, not the quarter of the invoice, so a note issued in a later quarter leaves the earlier return as it was and shows as a negative amount in the later one. A gateway refund note is not subtracted twice, because its refund already is. A draft or voided note reverses nothing. The Sales Tax report reads the same notes through one shared definition.

- Services: editing an active service's hosting account now checks its username against the cPanel account rules, and a name the panel would refuse is answered with `CPANEL_USERNAME_INVALID` instead of being saved.

- Installer: an upgrade now backs up the database first and can be rolled back. Running `install.sh` on an existing install dumps the database through the db container into `backups/` (file and folder readable by the owner only), in a file named with the UTC date, time and the `IMAGE_TAG` it belongs to, and stops before changing anything if the dump fails, is empty or is cut short (a finished dump ends with the pg_dump completion line). A stopped database whose volume exists is started on its own first; a first install that never started its database has nothing to back up and can be rerun. The newest 5 backups are kept (`--keep` or `HOSTPANEL_BACKUP_KEEP`) together with the oldest backup of each version and the one just made. `install.sh --rollback` returns to the newest backup whose version differs from the installed one: it asks for confirmation (`--yes` for scripts), stops the services listed by `docker compose config --services`, saves the current database as `pre-rollback-*`, restores the backup into a temporary database that replaces the live one only on success, then downloads the old compose files, sets `IMAGE_TAG`, pulls those images and starts the stack. A failure after the services were stopped prints the state and the exact commands to run. Uploads, plugin volumes and new `.env` keys are not rolled back. `--skip-backup` upgrades without a dump and leaves the data unprotected. A backup taken on the moving `latest` tag cannot be rolled back automatically, so pass `--version` on upgrades. Covered by `scripts/test-install-backup.sh`.

- Installer: follow ups to the rollback (#978). A rename of the restored database that a background database worker blocks is now tried again up to 10 times, ending the sessions that hold the database first; if it stays blocked the live database is put back and the message says the database was busy instead of calling the backup damaged. A rollback that would move to a newer version than the installed one (a repeated rollback) now says in bold that it moves forward and asks "Move FORWARD". After a failed restore the messages say exactly where the data is: the saved copy, the replaced database and the restored one, and no longer name the backup as the saved copy when the database had no tables. A rollback over a half finished swap is refused with the commands that put a database back. The oldest backup of a version is now kept for the newest 10 versions only (`--keep-versions` or `HOSTPANEL_BACKUP_KEEP_VERSIONS`), so the backups folder does not grow with every release. `--rollback` refuses a database named `postgres` before it changes anything, and the tests check that the volume name in the installer matches the compose file.

- Plugins: manage registry plugins from the admin panel (#1010). A card in Browse opens a details page with the publisher's links, the list of versions (status, host range, release notes, permissions), and an install of the version you choose, an update, a confirmed downgrade (`allowDowngrade`) and an uninstall. A paid or private plugin has a licence key card: the key is saved encrypted, write only, and sent to the registry as `X-Licence-Key`; a missing or refused key shows `PLUGIN_REGISTRY_LICENCE_REQUIRED` or `PLUGIN_REGISTRY_LICENCE_INVALID`. An install also refuses a yanked, compromised or host incompatible version (`PLUGIN_REGISTRY_VERSION_YANKED`, `PLUGIN_REGISTRY_VERSION_COMPROMISED`, `PLUGIN_REGISTRY_HOST_INCOMPATIBLE`), and a catalogue entry without a version is skipped instead of failing the page. New endpoints under `/api/admin/plugins`: `GET registry/{id}`, `PUT` and `DELETE registry/{id}/licence`, and `allowDowngrade` on `POST registry/{id}/install`.

- Docs: operator and developer pages for the plugin registry (#866). Plugin registry covers the settings and compose variables, the three registry trust values, that unsigned packages are never installed from a registry, the download limits, the PLUGIN_REGISTRY_* errors and the Browse tab. Plugin registry read contract covers the three read endpoints a registry must serve, anonymous reads, same origin downloads, the SHA-256 rule and how the base address relates to the upload path. A new admin end to end spec covers Browse then Install.

- Plugins: a preview can offer element selection to a chat, off unless the view declares it. One preview per document may offer it, a frame's messages are treated as claims, and the plugin's server names what is selected. A "try again" after the page changed is refused and asks the reader to select again, keeping the message.

- Billing: credit notes. Staff can issue a credit note against a paid invoice from the new Credit notes tab of the invoice, for all of it or part, with the tax following the invoice at the same rate. The value goes either to the client's credit balance (a new credit history line, "credit note") or back through the payment gateway as one refund of the invoice, so the money moves once and is counted once in the reports. A note can never credit more than the invoice charged less every earlier refund and every earlier credit note, also when two are issued at the same moment, and it is refused on a credit top-up and on an unpaid invoice. A note is numbered `CN-0001` and so on from its own counter, is never deleted and can only be voided with a reason (a note paid out as a gateway refund cannot be voided). Staff get a Credit Notes list, a page per note and a PDF; the client gets a Credit notes page in the client area, a PDF in their language (English, Russian or Armenian) and an email when a note is issued. The numbering is a cautious default that has not been checked against any local law and cannot promise there are no gaps; an operator must check what their jurisdiction requires. There is no tax authority integration.

- Billing: client wallet. A client has a Credit page in the client area with their balance, the history of every movement of it and an Add funds page. Adding funds raises a one-line top-up invoice in the client's billing currency, between a minimum and a maximum set in System Settings (`billing.credit.topup_min`, `billing.credit.topup_max`), paid through a bank transfer or an installed gateway. The balance rises exactly once when the invoice is paid, however the payment is confirmed or replayed, and the client is emailed the new balance. A top-up fulfils nothing, takes no credit and is refunded by hand only, which takes the refunded credit off the balance. The client can also apply credit to their own invoice. Every movement of the balance is recorded on the client ledger with its type, the signed change and the balance it left (new movement, change and balance columns on `Transactions` and an `IsCreditTopUp` column on `Invoices`; older entries are not itemised), and staff get a Credit tab on the client profile with the history and add or deduct with a reason. Ledger entries of the history cannot be edited or deleted, and credit that covers a whole invoice now settles it and fulfils its order.

- Billing: manual bank transfer. A client can choose it on the checkout and invoice pages: the invoice moves to Payment Pending and shows the bank details (account holder, bank, IBAN, SWIFT, instructions) with copy buttons and a reference built from the invoice number, and the client is emailed the same details. Staff get a notice, and a Pending Bank Transfers page under Billing lists each transfer to confirm (the invoice is paid like any other payment, so the receipt, the ledger and the order fulfilment follow) or reject with a note the client reads (the invoice is open again). A second confirm of the same transfer is refused. The bank details, including the new SWIFT field, are edited in the Bank Transfer integration settings. Uploading a payment receipt is not part of this change.

- Admin panel: an Upcoming Renewals page under Billing lists the services and domains renewing in the next 30, 60 or 90 days. A row switches automatic renewal on or off and raises that client's renewal invoice by hand. A third list shows paid domain renewal lines left claimed after the registrar gave no clear answer; staff release one after checking the registrar, and the release is written to the client's activity log.

### Fixed

With git and its helpers among the extras each key took about 20 seconds of CPU on a CWP server, longer than HostPanel's default 20 second SSH operation timeout, so a key could be reported failed although the agent added it. A jail still gets an extra added to the configuration, or a binary a package update replaced, on the next key.
- Payments: follow-ups to saving the payment method within the payment (#1164). The consent recorded when a payment that keeps the method is started is revoked when that payment will never store one: the gateway declined the session, a new attempt replaced it, or the invoice was settled another way. The gateway customer is no longer saved before the payment is registered, but in the same save as the session and the consent, so a payment that fails to register leaves no customer row. The wording version `2026-11`, which was accepted while the version was a free text, is refused now. The consent is also revoked when its invoice is cancelled (one, in bulk, or when a domain's renewal invoices are released) or paid another way, without waiting for the session to be checked. A guest who asks to keep the method on the order payment now gets a normal `UNAUTHORIZED` refusal (401) from the use case instead of an exception, and the refusal codes of the order payment start are documented.
- Plugins: the maintainer key that ships with the server now matches the key official plugins are signed with (`official-innovayse-2026`), so a fresh server installs an official plugin without the operator adding a key (#1155).
- Services: a plan change no longer gets stuck when its upgrade invoice is cancelled (#79). Cancelling the invoice an approved upgrade waits for, in any way, now rejects that request, so the service is free for a new plan change; before, the request stayed Approved until staff rejected it. The upgrade invoice also falls due after `Orders:InvoicePaymentTermDays` like an order's invoice, not after a fixed 7 days. In the Armenian interface the plan change screens of the client portal and the admin now both say «պլան» for a plan.
- Client area: one rule now decides whether a service needs setup (#717). Only a Pending hosting service shows "needs setup" and is sent to the setup wizard, in the lists, the dashboard, the detail page, its notices and its sidebar, as the backend setup accepts only a Pending service; an active service without a control-panel username is no longer sent to a wizard the backend would refuse. The setup page of a digital service shows the loading panel until it has redirected, so the wizard no longer flashes. `usePermissions` is removed; `Permission` now lives in `types/permission`. A layout test covers the navigation before the identity has loaded.
- cPanel servers: follow ups to the WHM provider. A single sign-on link is passed on only when it is an https address on the server's own host (otherwise `SERVICE_CPANEL_SSO_URL_UPSTREAM_FAILED`). The username of a new account and its domain are checked before WHM is called and a bad one stops the setup with `CPANEL_USERNAME_INVALID` or `CPANEL_DOMAIN_INVALID`; an empty value is never sent. A create call that could not be sent with a lookup that cannot say whether the account exists is now a temporary error instead of a refusal. A WHM reply over 16 MB is refused. `Provisioning__CPanelWhmPort` and `Provisioning__CPanelUserPort` must be 1 to 65535 or the host does not start. The Use SSL for connections field is ignored for cPanel, which is documented.
- cPanel servers: small follow ups. When a create call and the lookup after it are both lost, setting up the service now answers 503 `PROVISIONING_OUTCOME_UNKNOWN` (try again) instead of the refusal code `PROVISIONING_UPSTREAM_FAILED`, and the service stays Pending. A single sign-on link is accepted only on the cPanel port (`Provisioning__CPanelUserPort`), and the browser is given the parsed address that was checked. Saving the hosting account of a service on a cPanel server, and adding an existing account to one, now checks the username at once and answers `CPANEL_USERNAME_INVALID` instead of failing later at provisioning.
- Storefront: the plan toggle on the home and hosting pages now offers every billing cycle the shown plans are priced on (monthly, quarterly, semi-annual, annual and biennial), in that order, instead of only monthly and yearly, and each card shows its price per month for the chosen cycle. A plan priced only on a longer cycle can be ordered from the home page, and the toggle scrolls inside its own track when there are many cycles. The cycle labels are the ones the hosting page already uses.
- Storefront slides: the public slides feed carries a new `pricing.fromPrice`, the lowest monthly equivalent across every cycle the linked product is priced in (monthly, quarterly, semi-annual, annual and biennial, each price divided by the months of its cycle). A product priced only quarterly, semi-annually or biennially now has a from price instead of none; `monthlyPrice` and `annualPrice` are unchanged.
- Services: the credentials of a hosting service are now read from the control panel of the server the service is on, as the sign-in link already was, instead of fixed development values. A service with no server assigned answers that it has none.
- Services: a terminated service no longer reaches the hosting panel when its password or package is changed, its credentials are read or a sign-in link is asked for; each now answers that the service is not active, also when the same account reference has since been given to another service. The client area hides the webmail link and the password and SSH panels for a terminated service.
- Single sign-on: repeated sign-in attempts can no longer lock a browser out of the client area. The page to return to is now limited to 512 bytes (it was 1024 characters, which with multibyte characters and five open attempts could exceed the 8 KB request header limit and get every request answered with 400), a silent attempt is dropped before an interactive one when a browser holds too many, and a deployment with no session encryption key now refuses to start a sign-in instead of sealing it under a key that differs per replica and restart.
- Single sign-on: signing out of every application at the sign-on provider now ends the admin session here too. The API was started without the provider's issuer, so every back-channel logout was refused with a 400 and the session stayed alive. The compose files pass it through as `SSO_ISSUER` (copy the `issuer` value from the provider's `/.well-known/openid-configuration`, trailing slash included), and the API now refuses to start under `AUTH_MODE=sso` while it is empty. Set `SSO_ISSUER` before updating a single sign-on deployment.
- Billing: a card payment finished after the client chose a manual bank transfer is no longer lost. The invoice keeps the card session, the reconciler keeps asking the gateway about it while a transfer waits (however old the session is), and a full card payment settles the invoice and ends the wait. When staff had already confirmed the transfer, the card money goes to the client's credit balance, also when the transfer was confirmed more than a day after the session began.
- Billing: a bank transfer nobody confirms no longer pauses the overdue and suspension rules for good. A transfer that waits longer than the number of days set in the Bank Transfer integration (14 when blank) lapses, the client is emailed, and the invoice is open again, Overdue when its due date has passed; a reject after the due date also returns it to Overdue. Bank transfer is offered only while at least one bank detail or the instructions are filled in, and the client sees a notice to contact the provider when a waiting transfer has none.
- Billing: an account credit note is refused while a gateway refund of the same invoice is still waiting for its gateway, and the amount of that refund is held out of what a note may credit. A client can hold at most `billing.credit.topup_max_open` unpaid top-up invoices (3 by default), and a bulk duplicate skips a credit top-up instead of failing the other copies.
- Billing: the Credits Reviewer report lists every movement of the credit balance (paid top-ups, credit notes, staff adjustments, credit applied) with its signed change, and the Sales Tax report subtracts the tax of the account credit notes issued in the period.
- Billing: raising renewal invoices for one client now runs under a per-client database lock, so the daily run and a staff click (or two instances) can no longer both pass the duplicate check and bill the same renewal twice.

- Plugins: two first writes of one plugin key at the same time could fail with an out of range error instead of being retried. The store now retries the write from a fresh read.
- Client portal: choosing another account in the header account menu, or "Add another account", started the sign-in with the wrong application and callback, so the person landed on a page that does not exist and kept the old account. The header widget is now served from the portal itself, so both go through the portal's own sign-in and end back in the portal as the chosen account.
- Admin panel: the theme script in `index.html` was blocked by the Content-Security-Policy on every load. It is now a file served from the panel's own origin, and the policy stays free of `unsafe-inline` for scripts.
- Admin panel: when the identity provider signs a person out everywhere, the API must be registered with it as the receiver (`/api/auth/backchannel-logout`) for this client, otherwise the admin session outlives the sign-out (see the Docker README).
- Admin panel: the container refused to start with "DOCS_URL must be empty or an http(s) address" when `DOCS_URL` (or `CLIENT_BASE_URL`) was left empty, the value the settings document as allowed. An empty value is accepted again and a malformed one is still refused.
- Plugins: a plugin was skipped at start with "Entry point type not found" because the published image stamped the plugin SDK assembly with the image version (0.0.0.0 in a default build) instead of its own, so no plugin built against the SDK could load. The image version no longer reaches the SDK, and the log now says why an entry point type could not be loaded.

### Changed

- Upgrade note: Saved card customers from earlier versions are copied to the new per-gateway table as customers of the plugin with the id `stripe`, because the only gateway that ever wrote them was that one. No card plugin is publicly available yet, so these references are kept and used once a plugin with that id is installed. If your card gateway plugin uses another id, install the plugin as `stripe`, or rewrite `GatewayModuleId` in `GatewayCustomers` to your plugin id before clients pay with a saved card; otherwise those clients are asked for their card again. The plugin assembly conflict check (`PLUGIN_ASSEMBLY_CONFLICT`) applies to every DLL in a package, shared third-party libraries included, so two plugins cannot ship a library of the same file name (#871).
- Single sign-on builds use the newer sign-on package. The first update signs every admin panel user out once, because the package now scopes its session cache keys per product. A sign-in callback with no matching attempt (a second tab, Back after signing in) takes a signed-in person to the dashboard and anyone else to the sign-in page instead of answering an error body, and two sign-ins started in one browser no longer spend each other (#822, #796).

- Before upgrading a production server that has uploaded plugins: plugins in the upload folder carry no signature yet, so after this release they are skipped at start (the log names each one) until the plugin is replaced by a signed package, or an administrator switches on "Allow unsigned plugins" on the Plugins page and the server is restarted. Plugins shipped inside the server image keep loading (#638, #789).
- Ledger transactions record where they came from (gateway payment, gateway refund, manual entry or import), and a gateway payment can be recorded only once per payment method and reference. Manual entries and imports may still share a reference. Before upgrading, `scripts/check-duplicate-gateway-payments.sh` lists existing gateway payment rows that share a reference; the upgrade stops and names them if any are left (#754).
- The plugin SDK is `Hostpanel.Sdk`, renamed from `Innovayse.SDK`: the package id, the assembly and every namespace (`Hostpanel.Sdk.Plugins.*`, `Hostpanel.Sdk.Base`) changed. A plugin rebuilds against the new package and updates its `using` lines; the host still refuses a package that ships either `Hostpanel.Sdk.dll` or the old `Innovayse.SDK.dll`. It is MIT licensed, so a plugin may be free or paid, open or closed source, while the rest of the repository stays AGPL-3.0-or-later. It lives in its own repository, [innovayse/hostpanel-sdk](https://github.com/innovayse/hostpanel-sdk), with its history, and is included here as a git submodule at `backend/src/Hostpanel.Sdk`. Clone with `git clone --recurse-submodules`, or run `git submodule update --init` after a plain clone. The package is built and published from that repository, ships with its license text and a readme that shows how to pin a version and write a minimal plugin, and this repository no longer publishes it. Stored plugin settings and data are unchanged (#623, #625, #846).
- Gateway payment reconciliation no longer gives up on a payment that is still pending after 24 hours. It asks the gateway again with a doubling wait (5 minutes at first, at most 6 hours, set in `ScheduledJobs`) until the gateway gives a final answer, and staff are mailed once per payment when it stays pending for 24 hours (#571).
- Automatic termination of a long suspension waits `billing.renewal.terminate_after_suspended_days` (default 14) instead of a fixed 14 days, and staff are mailed when the hosting account cannot be removed; the service stays suspended and the next run retries it (#571).
- Recurring jobs may run as long as their lease (`ScheduledJobs:LeaseMinutes`) instead of being cancelled after one minute (#571).
- A production host loads message handler code generated when the image is built instead of compiling every handler on its first use, which keeps the API's memory flat after a restart (#589, #592).
- A client no longer reads an invoice that is still a draft through any invoice route; it answers like an invoice that does not exist (#571).
- Billing cycles and domain actions are enums end to end. The API sends and accepts the billing cycle of a service or order line as `Monthly` or `Annual` (the old `annually` spelling is no longer accepted on the wire) and a domain action as `Register`, `Transfer` or `Renew`; stored values written in the older spellings are still read, and the release rewrites them to `Monthly` or `Annual`. The TLD price table now lists its extensions as an array of entries that each carry their `tld`. Importing a service or order that names a cycle other than monthly or annual is skipped and logged instead of being stored on a guessed cycle (#571).
- Recurring billing engine: a renewal invoice is raised 14 days before a service or domain falls due (`billing.renewal.invoice_days_before`), reminders go out 7, 3 and 1 days before (`billing.renewal.reminder_days`), and paying the invoice is what extends the service or renews the domain, exactly once. Credit is applied to renewal invoices automatically (`billing.renewal.auto_apply_credit`). The next period is raised only after the previous one is paid, at most once per daily run; a period that already started (a back-dated renewal date) gets the normal payment window, due 14 days after it is raised, instead of being born overdue (#477).
- Overdue suspension: any overdue invoice, renewal or not, gets a grace period after its due date (`billing.renewal.suspend_after_overdue_days`, default 3), then only the services on its lines are suspended. An overdue invoice with no service lines now suspends nothing (it used to suspend every service of the client). Paying lifts a suspension made for an overdue invoice once no other overdue invoice covers the service, and the daily renewal run lifts any that were missed; a suspension made by an operator, or for an expired domain, is never lifted by a payment (#477).
- An operator who unsuspends a service that is still on an invoice overdue past the grace sees it suspended again at the next 09:00 run, unless the service has `OverrideAutoSuspend` set or a `SuspendUntil` date in the future (#477).
- Cancelling a renewal invoice does not stop the renewal: the period is invoiced again on the next daily run while it is due. To stop a service renewing, set `AutoTerminateEndOfCycle` or open a cancellation request until the admin auto-renew toggle lands. A service skipped that way whose renewal date has already passed is running unbilled; a Warning says so on every run, and one Warning per run counts auto-renewing services that have no renewal date at all (`NextRenewalAt` empty) and are never billed (#477).
- Domains are no longer renewed for free: auto-renewal now bills the client, and the registrar is called only once the invoice is paid. A failed or unconfirmed registrar renewal alerts staff (`Notifications__AdminEmail`, falling back to `Notifications__ContactEmail`). A client renew order takes the domain off any open renewal invoice first, returning that invoice's credit; an overdue invoice that bills the domain with other items, or a renewal invoice with a payment in progress (PaymentPending) or in Collections, has to be settled first (`RENEWAL_INVOICE_OPEN`, 409). While that renew order is unpaid the daily run does not bill the domain again. An auto-renewing domain still gets the expiry warnings unless its renewal invoice is open and renewal reminders are on (#477, #488).
- Rollout note: on first deploy, (1) any service whose `NextRenewalAt` is already in the past gets a renewal invoice immediately, due 14 days later; (2) at the first 09:00 run every Active service on an invoice, including invoices raised before this release, that is already overdue by more than 3 days is suspended. Run the query below after the upgrade and before the first 09:00 run to list them, and set `OverrideAutoSuspend`/`SuspendUntil` or settle the invoices where a suspension is not wanted (#477):

  ```sql
  SELECT i."Id" AS "InvoiceId", i."ClientId", i."DueDate", it."ClientServiceId", s."OverrideAutoSuspend", s."SuspendUntil"
  FROM "Invoices" i
  JOIN "InvoiceItems" it ON it."InvoiceId" = i."Id"
  JOIN "ClientServices" s ON s."Id" = it."ClientServiceId"
  WHERE i."Status" = 'Overdue'
    AND i."DueDate" < now() - interval '3 days'
    AND s."Status" = 'Active'
  ORDER BY i."ClientId", i."Id";
  ```

  Set `Notifications__AdminEmail` (or rely on `Notifications__ContactEmail`) so renewal alerts reach a person.

  Services suspended before this release have no recorded suspension source, so no payment lifts them automatically (only an overdue suspension is lifted by payment). Review them by hand after deploying (`SELECT "Id", "ClientId" FROM "ClientServices" WHERE "Status" = 'Suspended' AND "SuspensionSource" IS NULL;`). Renewing a domain still lifts the suspension of its linked hosting service, as before. `billing.renewal.invoice_days_before` must be 1 to 90; a stored 0 is read as the default 14, with a warning in the log.
