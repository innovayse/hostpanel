# Հետգրում {#rollback}

Ինչպես վերադառնալ Hostpanel-ի նախորդ թողարկմանը, երբ թարմացումը խնդիր է առաջացնում։

<Callout type="warning">
Եթե նոր տարբերակը տվյալների բազայի միգրացիա է ավելացրել, նախ վերականգնեք թարմացումից առաջ վերցրած դամփը. միգրացիաները հետ չեն կատարվում։ Հին պատկերները միգրացված տվյալների բազայի վրա գործարկելը կարող է տվյալների վնասման պատճառ դառնալ։
</Callout>

## Հետգրելուց առաջ {#before-you-roll-back}

Ստուգեք՝ արդյոք այն թողարկումը, որից հետ եք գնում, տվյալների բազայի միգրացիաներ է ավելացրել։
Եթե այո, հետգրման մաս պետք է կազմի թարմացումից առաջ վերցրած դամփի վերականգնումը։

## Հետգրում տեղադրիչով {#roll-back-with-the-installer}

Տեղադրիչով կատարված յուրաքանչյուր թարմացում թողնում է տվյալների բազայի պահուստային պատճեն՝
իր տարբերակի անվամբ (տե՛ս [Թարմացում](/hy/operators/upgrade))։ `--rollback`-ը օգտագործում է ամենաթարմ
պահուստային պատճենը, որի տարբերակը տարբերվում է `.env`-ի `IMAGE_TAG`-ից։ Վատ տարբերակի վրա
տեղադրիչը նորից գործարկելը նույն տարբերակի ավելի թարմ պահուստային պատճեններ է ստեղծում. դրանք բաց են
թողնվում, ուստի հետգրումը շարունակում է գնալ այն տարբերակին, որից թարմացրել եք։ Երբ տեղադրիչը
կտրում է հին պահուստային պատճենները, այն պահում է ամենաթարմ 10 տարբերակից յուրաքանչյուրի ամենահին
պահուստային պատճենը (`--keep-versions <n>`), որպեսզի այն չկորչի։ Այստեղ «ամենաթարմ» նշանակում է այն տարբերակը,
որի ամենաթարմ պահուստային պատճենը ամենավերջինն է, ոչ թե տարբերակի ամենաբարձր համարը. 0.3.1-ին հետգրելուց հետո
տարբերակները դասավորվում են ըստ այն բանի, թե երբ է վերջին անգամ պահուստավորվել յուրաքանչյուրը։
Ավելի հեռու տարբերակների ամենահին պահուստային պատճենները ջնջվում են ինչպես ցանկացած այլ հին
պահուստային պատճեն, ուստի թղթապանակը չի մեծանում յուրաքանչյուր թողարկման հետ։

Կրկնվող հետգրումը կարող է ընտրել **ավելի նոր** տարբերակի պահուստային պատճեն. 0.4.0-ից 0.3.1-ին հետ
գնալուց հետո մեկ այլ տարբերակի ամենաթարմ պահուստային պատճենները 0.4.0-ինն են։ Այդ դեպքում տեղադրիչը
թավ տառերով ասում է, որ սա **առաջ** է տանում, անվանում է երկու տարբերակները և հարցնում է
`Move FORWARD to <version>?`։ Պատասխանեք «ոչ», եթե նկատի ունեիք ավելի հետ գնալ, և նախ ավելի նոր ֆայլերը
հանեք `backups/`-ից։

```bash
curl -fsSL   https://raw.githubusercontent.com/innovayse/hostpanel/main/install.sh   | bash -s -- --rollback
```

`/opt/hostpanel`-ում չգտնվող տեղադրման համար ավելացրեք `--dir <path>`։ Այնուհետև այն՝

1. Ցույց է տալիս պահուստային պատճենը, որը կօգտագործի, և տարբերակը, որին կվերադառնա, և հաստատում է հարցնում։
   Սկրիպտում նախապես հաստատելու համար ավելացրեք `--yes`։ Առանց տերմինալի և առանց `--yes`-ի այն
   կանգ է առնում և ոչինչ չի փոխում։ Պահուստային պատճենը, որը դատարկ է կամ չի ավարտվում
   `-- PostgreSQL database dump complete` տողով, մերժվում է։
2. Եթե տվյալների բազան կանգնած է, գործարկում է այն առանձին, սպասում է, մինչև այն միացումներ ընդունի,
   և կանգնեցնում է `docker compose config --services`-ով թվարկված մյուս բոլոր ծառայությունները։
3. Ընթացիկ տվյալների բազան պահում է `backups/pre-rollback-<date>-<time>-<version>.sql` ֆայլում
   (UTC), որպեսզի հետգրումն ինքն էլ հնարավոր լինի չեղարկել։ Եթե այդ պատճենը հնարավոր չէ պատրաստել, այն կանգ է առնում
   ինչ-որ բան փոխարինելուց առաջ։ Առանց աղյուսակների տվյալների բազան պատճենի արժանի չէ, և ոչ մի պատճեն
   չի պահվում։
4. Պահուստային պատճենը վերականգնում է ժամանակավոր տվյալների բազայի մեջ և վերանվանում է այն
   գործող տվյալների բազայի տեղում միայն այն դեպքում, երբ ամբողջ վերականգնումն անցել է։ Ձախողված
   վերականգնումը, օրինակ՝ վնասված դամփի պատճառով, գործող տվյալների բազան թողնում է ճիշտ այնպես, ինչպես կար։
   Տվյալների բազան չի կարելի վերանվանել, քանի դեռ որևէ սեսիա այն պահում է, իսկ սերվերն ունի
   ֆոնային աշխատողներ (առաջին հերթին autovacuum), որոնք միանում են ինքնուրույն։ Ուստի յուրաքանչյուր
   վերանվանում նախ ավարտում է տվյալների բազան պահող սեսիաները և փորձվում է մինչև 10 անգամ՝
   վայրկյան տարբերությամբ։ Եթե այն մնում է արգելափակված, գործող տվյալների բազան վերադարձվում է իր տեղը,
   տեղադրիչն ասում է, որ տվյալների բազան զբաղված է մնացել (և ոչ թե որ պահուստային պատճենը կարող է վնասված լինել)
   և տպում է հետգրումը նորից գործարկելու հրամանը, որը կրկնել կարելի է անվտանգ։ Զբաղված է համարվում
   միայն այն վերանվանումը, որը սերվերը մերժում է որպես «in use»։ Ցանկացած այլ մերժում (իրավունք, լիքը
   սկավառակ, բացակայող տվյալների բազա) կանգ է առնում անմիջապես, տպում է սերվերի սեփական հաղորդագրությունը և ասում,
   որ գործող տվյալների բազան չի փոխվել կամ վերադարձվել է իր տեղը. վերացրեք այդ պատճառը, նախքան
   հետգրումը նորից գործարկելը։
5. Միայն հիմա է ներբեռնում հին տարբերակի compose ֆայլը և Caddyfile-ը, սահմանում է
   `IMAGE_TAG`-ը, ներբեռնում է այդ պատկերները և գործարկում համակարգը։ Այսպիսով 1-ից 4-րդ քայլերում ձախողումը
   թողնում է ընթացիկ compose ֆայլը տեղում։
6. Հեռացնում է `--keep`-ից ավելի հին `pre-rollback-*` ֆայլերը, բացառությամբ յուրաքանչյուր տարբերակի
   ամենահինի։ Սա տեղի է ունենում միայն վերականգնման հաջողվելուց հետո և երբեք նոր պատրաստված պատճենի հետ։

<Callout type="danger">
Հետգրումը վերջնականապես հեռացնում է պահուստային պատճենը վերցնելուց հետո գրված ամեն ինչ՝ պատվերներ, վճարումներ, աջակցության հայտեր և ցանկացած այլ տվյալ։ 3-րդ քայլում պահված պատճենը դրանց վերադառնալու միակ ճանապարհն է։
</Callout>

Եթե ծառայությունները կանգնեցնելուց հետո ինչ-որ բան ձախողվի, տեղադրիչը տպում է, թե ինչ վիճակում է
տեղադրումը, և գործարկման ճշգրիտ հրամանները։ Ձախողված վերականգնման դեպքում սա գործարկման հրամանն է և,
այն դեպքի համար, երբ տվյալների բազան սխալ է երևում, հրամանը, որը `pre-rollback` ֆայլը
ձեռքով վերադարձնում է տեղը՝

```bash
cd /opt/hostpanel && docker compose -f docker-compose.hub.yml up -d
```

Յուրաքանչյուր հաղորդագրություն ճշգրիտ ասում է, թե որտեղ են տվյալները։ Եթե փոխանակումն ինքնին կիսատ մնա,
գործող տվյալների բազան բացակայում է. հետգրումից առաջվա տվյալները դեռ գտնվում են
`<name>_replaced` տվյալների բազայում, վերականգնվող պահուստային պատճենը՝ `<name>_restore`-ում (երկուսն էլ
տվյալների բազայի կոնտեյների ներսում, `<name>`-ը `POSTGRES_DB`-ն է), իսկ `pre-rollback`
ֆայլը նույն տվյալներն է պարունակում, ինչ `<name>_replaced`-ը։ Տեղադրիչը տպում է հրամանը,
որը դրանցից մեկը վերանվանում է հետ իր տեղը, ապա՝ գործարկման հրամանը։ Մինչև գործող անունով տվյալների բազա
չլինի, նոր `--rollback`-ը մերժվում է ինչ-որ բան փոխելուց առաջ,
քանի որ նրա առաջին քայլը երկու մնացորդներն էլ կջնջեր։ Երբ տվյալների բազան աղյուսակներ չի ունեցել,
`pre-rollback` պատճեն չի պատրաստվում, և հաղորդագրությունը դա ասում է՝ ֆայլ անվանելու փոխարեն։

Եթե վերականգնումը ընդհատվի (տեղադրիչը սպանվի, կամ `docker compose exec`-ը ձախողվի),
տեղադրիչը չի կռահում. այն կարդում է, թե `<name>`, `<name>_replaced` և `<name>_restore` տվյալների բազաներից
որոնք են այժմ գոյություն ունեն, և ասում, թե դա ինչ է նշանակում, օրինակ՝ որ գործող տվյալների բազան բացակայում է, կամ որ այն
հավանաբար պարունակում է վերականգնված պահուստային պատճենը, իսկ հին տվյալները `<name>_replaced`-ում են։ Երբ նույնիսկ
այդ ցուցակը հնարավոր չէ կարդալ, այն ասում է, որ վիճակն անհայտ է, և տպում է տվյալների բազաները թվարկող հրամանը։

`postgres` անունով տվյալների բազան հնարավոր չէ հետգրել տեղադրիչով. վերականգնումը տվյալների բազաները
փոխում է՝ դրանք վերանվանելով `postgres` սպասարկման տվյալների բազայից, ուստի
`--rollback`-ը մերժում է այն ինչ-որ բան փոխելուց առաջ։ Վերականգնեք այն ձեռքով՝ ինչպես նկարագրված է ստորև՝
[`postgres` անունով տվյալների բազա](#a-database-named-postgres) բաժնում։

Հետգրումը չի չեղարկում այն ամենը, ինչ թարմացումը կարող էր փոխել։ Վերբեռնված ֆայլերը և
պլագինների ծավալները տվյալների բազայի դամփի մաս չեն և մնում են ինչպես կան, իսկ բանալիները,
որ նոր թողարկումն ավելացրել է `.env`-ում, մնում են դրանում (չօգտագործվող բանալիները վնասակար չեն, բայց քննարկեք
դրանք)։ Հետ են գնում միայն տվյալների բազան, compose ֆայլը, Caddyfile-ը և `IMAGE_TAG`-ը։

`--rollback`-ը չի կարելի համադրել `--version`-ի հետ, քանի որ տարբերակը այն է, որը գրանցված է
պահուստային պատճենի հետ։ Պահուստային պատճենը, որը վերցվել է այն ժամանակ, երբ `IMAGE_TAG`-ը `latest` էր,
մերժվում է. վերականգնեք այն ձեռքով՝ ինչպես նկարագրված է ստորև։ Ընտրվածից ավելի հին պահուստային պատճեն օգտագործելու համար
նախ ավելի նոր ֆայլերը հանեք `backups/`-ից կամ հետևեք ձեռքի քայլերին։

## Հետգրում ձեռքով {#roll-back-by-hand}

**1. Կանգնեցրեք հավելվածի կոնտեյները** (տվյալների բազան թողեք աշխատող)՝

```bash
cd /opt/hostpanel
docker compose -f docker-compose.hub.yml stop \
  hostpanel-api hostpanel-client hostpanel-admin hostpanel-caddy
```

**2. Եթե նոր թողարկումը միգրացիաներ է ավելացրել, տեղադրիչը գործարկելուց առաջ վերականգնեք թարմացումից առաջ վերցրած տվյալների բազայի դամփը՝**

<Callout type="danger">
Թարմացումից առաջ վերցրած դամփի վերականգնումը վերջնականապես հեռացնում է թարմացումից հետո գրված ամեն ինչ՝ պատվերներ, վճարումներ, աջակցության հայտեր և ցանկացած այլ տվյալ։ Շարունակելուց առաջ համոզվեք, որ ճիշտ դամփի ֆայլ ունեք։
</Callout>

`pre-upgrade-2024-01-15-103000.sql`-ը փոխարինեք թարմացման 1-ին քայլում ստեղծված ամսաթվով ֆայլով։

```bash
cd /opt/hostpanel

# Safety dump of the current (migrated) state:
umask 077
docker compose -f docker-compose.hub.yml exec -T hostpanel-db \
  sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  > pre-rollback-$(date +%Y-%m-%d-%H%M%S).sql

# Verify the pre-upgrade dump file (a finished dump ends with the pg_dump completion line),
# then drop and restore. A damaged dump restored this way leaves the database empty,
# so keep the pre-rollback file above until the stack works:
if ! test -s pre-upgrade-2024-01-15-103000.sql || ! tail -n 5 pre-upgrade-2024-01-15-103000.sql | grep -q "^-- PostgreSQL database dump complete$"; then
  echo "Dump file is empty, cut short or missing, aborting."
else
  docker compose -f docker-compose.hub.yml exec -T hostpanel-db \
    sh -c 'dropdb -U "$POSTGRES_USER" "$POSTGRES_DB" && \
           createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'
  docker compose -f docker-compose.hub.yml exec -T hostpanel-db \
    sh -c 'psql -v ON_ERROR_STOP=1 --single-transaction \
           -U "$POSTGRES_USER" "$POSTGRES_DB"' < pre-upgrade-2024-01-15-103000.sql
fi
```

**3. Հետ գրեք compose ֆայլերը, Caddyfile-ը և `IMAGE_TAG`-ը** տեղադրիչով՝

```bash
curl -fsSL \
  https://raw.githubusercontent.com/innovayse/hostpanel/main/install.sh \
  | bash -s -- --version 1.3.2
```

Սա compose ֆայլը և Caddyfile-ը վերադարձնում է հին տարբերակին, սահմանում է `IMAGE_TAG`-ը,
ներբեռնում է հին պատկերները և գործարկում համակարգը։ `1.3.2`-ը փոխարինեք այն տարբերակով, որին
հետ եք գնում՝ թարմացման 1-ին քայլում նշած արժեքով։

**4.** Ստուգեք, որ `GET /health`-ը վերադարձնում է `200` և որ կարող եք մուտք գործել։

## `postgres` անունով տվյալների բազա {#a-database-named-postgres}

`POSTGRES_DB=postgres`-ը սերվերի սեփական սպասարկման տվյալների բազան է։ Չի կարելի ջնջել այն
տվյալների բազան, որին միացած եք, ուստի վերը նկարագրված ձեռքի քայլերը, որոնք `POSTGRES_DB`-ում նշված
տվյալների բազայի դեմ գործարկում են `dropdb` և `createdb`, դրա համար չեն աշխատում։ Ջնջելու և ստեղծելու համար միացեք
մեկ այլ տվյալների բազայի և միայն դրանից հետո բեռնեք դամփը։
`template1`-ը գոյություն ունի ամեն սերվերում և սովորական ընտրությունն է։ Նախ կանգնեցրեք հավելվածի
կոնտեյները (վերևի 1-ին քայլ) և վերցրեք 2-րդ քայլի պահպանողական դամփը։

```bash
cd /opt/hostpanel

# Drop and create from template1, ending any other session that holds postgres.
# Both commands run in the database container, as POSTGRES_USER.
docker compose -f docker-compose.hub.yml exec -T hostpanel-db \
  sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d template1 \
           -c "DROP DATABASE IF EXISTS postgres WITH (FORCE)" \
           -c "CREATE DATABASE postgres"'

# Load the dump into the new postgres database.
docker compose -f docker-compose.hub.yml exec -T hostpanel-db \
  sh -c 'psql -v ON_ERROR_STOP=1 --single-transaction \
         -U "$POSTGRES_USER" -d postgres' < pre-upgrade-2024-01-15-103000.sql
```

`WITH (FORCE)`-ը պահանջում է PostgreSQL 13 կամ ավելի նոր տարբերակ։ Ավելի հին սերվերի վրա սեսիաները նախ
ավարտեք `template1`-ից՝ `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = 'postgres' AND pid <> pg_backend_pid()`
հարցմամբ, ապա ջնջեք առանց `FORCE`-ի։ Վնասված դամփը նոր տվյալների բազան թողնում է
դատարկ, ուստի նախ ստուգեք դամփը 2-րդ քայլի `tail` ստուգմամբ և պահեք պահպանողական դամփը,
մինչև համակարգը չաշխատի։ Ապա շարունակեք 3-րդ քայլով։

## Հետգրումից հետո {#after-rolling-back}

Բացեք սխալի մասին հաշվետվություն՝ նկարագրելով, թե ինչը սխալ գնաց, որպեսզի խնդիրը ուղղվի
հաջորդ թողարկումում։ Նշեք տարբերակը, որից հետ եք գնացել, և API-ի մատյանում տեսած սխալը՝

```bash
cd /opt/hostpanel && docker compose -f docker-compose.hub.yml logs hostpanel-api
```
