# Թարմացում {#upgrade}

Ինչպես անցնել Hostpanel-ի նոր թողարկման՝ տեղադրիչով կամ ձեռքով՝
docker compose-ի միջոցով։

## Թարմացնելուց առաջ {#before-you-upgrade}

<Callout type="warning">
Յուրաքանչյուր թարմացումից առաջ վերցրեք տվյալների բազայի դամփ։ Տվյալների բազայի միգրացիաները ավտոմատ կատարվում են առաջ API-ի յուրաքանչյուր գործարկման ժամանակ և հետ չեն կատարվում։ Եթե հետ վերադառնալու կարիք լինի, ձեզ դամփ կպահանջվի։ Տեղադրիչը այն վերցնում է ձեր փոխարեն (տե՛ս <a href="#upgrade-with-the-installer">Թարմացում տեղադրիչով</a>), իսկ ձեռքով թարմացման դեպքում պետք է վերցնեք ձեր սեփականը։ Տե՛ս <a href="/hy/operators/backup">Պահուստավորում և վերականգնում</a>։
</Callout>

Թարմացնելուց առաջ կարդացեք նոր թողարկման changelog-ի գրառումը։ Վերցրեք տվյալների բազայի
դամփ և նկատի առեք `/opt/hostpanel/.env`-ում ընթացիկ `IMAGE_TAG`-ը։ Այն ձեզ պետք
կգա հետգրման դեպքում։

### Ստուգեք վճարային համակարգի կրկնվող վճարումները {#check-for-duplicate-gateway-payments}

0.4.0 թողարկումը ավելացնում է եզակի ինդեքս վճարային համակարգի վճարումների հղումների վրա։ Եթե վճարային համակարգի
երկու վճարման տող ունեն միևնույն վճարման եղանակը և հղումը, միգրացիան կանգ է առնում,
և թարմացումը ձախողվում է։ Թարմացնելուց առաջ գործարկեք ստուգման սկրիպտը։ Դատարկ արդյունքը նշանակում է,
որ միգրացիան կանցնի առանց խնդիրների։

Սկրիպտը 0.4.0 թողարկման մաս է։ Այն աշխատում է և՛ 0.3.x, և՛ 0.4.0 տվյալների բազայի վրա,
ուստի գործարկեք այն թարմացումից առաջ։ Ստացեք այն թողարկման թեգից՝

```bash
curl -fsSL -o /tmp/check-dup-payments.sh \
  https://raw.githubusercontent.com/innovayse/hostpanel/v0.4.0/scripts/check-duplicate-gateway-payments.sh \
  && sh /tmp/check-dup-payments.sh hostpanel-db
```

Սկրիպտը նախ ներբեռնելը նշանակում է, որ ձախողված ներբեռնումը դատարկ պատասխան չի փոխանցի
`sh`-ին։ Առաջին արգումենտը տվյալների բազայի կոնտեյների անունն է (լռելյայն՝ `hostpanel-db`)։
Եթե ձեր կոնտեյները այլ անուն ունի, փոխանցեք այն։

Եթե սերվերը դուրս գնացող ինտերնետ հասանելիություն չունի, պատճենեք սկրիպտը ռեպոզիտորիայից
և գործարկեք SSH-ով՝

```bash
ssh user@your-server 'sh -s -- hostpanel-db' < scripts/check-duplicate-gateway-payments.sh
```

Եթե սկրիպտը տողեր է թվարկում, յուրաքանչյուրին տվեք առանձին հղում (կամ ջնջեք
կրկնօրինակը), ապա թարմացնելուց առաջ նորից գործարկեք այն։

### Տվյալների բազան վերանվանվում է {#the-database-is-renamed}

0.4.0 թողարկումը յուրաքանչյուր աղյուսակ, բանալի, ինդեքս և սահմանափակում վերանվանում է PascalCase (սյունակներն
արդեն այդպես էին)։ Միգրացիան վերանվանում է դրանք տեղում և պահպանում է ամբողջ տվյալները։ Թարմացրեք ձեր սեփական
SQL-ը, հաշվետվությունները և սկրիպտները նոր անուններով։ Թարմացումից առաջ վերցրած դամփը վերականգնվում է միայն
նախորդ տարբերակի վրա, ուստի պահեք այն հետգրման համար և մի վերականգնեք 0.4.0-ի վրա։

### Կարգավորումներ, որոնք պետք է սահմանված լինեն {#configuration-that-must-be-set}

0.4.0 թողարկումը պահանջում է այս կարգավորումները։ Սահմանեք դրանք `.env`-ում առաջին գործարկումից առաջ՝

- `ENCRYPTION_KEY` ամեն միջավայրում։
- `SESSION_ENCRYPTION_KEY` հաճախորդի հավելվածի սեսիաների համար։ Տեղադրիչը ստեղծում է այն ձեր փոխարեն։
- `EDGE_SCHEME`՝ սխեման, որով հասանելի են հանրային հոսթերը (`https://` կամ `http://`)։
- Վստահելի պրոքսիների քանակները `RateLimit`-ի տակ (`KnownProxies`, `KnownNetworks`, `TrustedProxyCount`)։
- Բացարձակ `Cors:AllowedOrigins` գրառումներ, ինչպես `https://host.example.com`։

Production-ում API-ն չի գործարկվում, քանի դեռ որևէ գաղտնիք տեղապահ արժեք է պարունակում։

### Պահված քարտեր և վճարային պլագին {#saved-cards-and-the-payment-plugin}

0.4.0 թողարկումը հեռացնում է ներկառուցված քարտային վճարային համակարգերը։ Դրանց պլագինները դեռ
հանրությանը հասանելի չեն, ուստի եթե քարտով վճարումներ եք ընդունում, մնացեք 0.3.1-ի վրա, մինչև քարտային
պլագին հասանելի դառնա։ Առանց քարտային պլագինի checkout-ում քարտային վճարման եղանակ չի առաջարկվում։
Բանկային փոխանցումը շարունակում է աշխատել։

Թարմացումը պահպանում է պահված քարտերի հաճախորդների հղումները։ Այն դրանք տեղափոխում է `stripe`
id-ով վճարային պլագինին, քանի որ դրանք երբևէ պահել է միայն այդ վճարային համակարգը, և դրանք
օգտագործվում են, երբ այդ id-ով պլագին տեղադրվի։ Եթե ձեր պլագինը այլ id է օգտագործում,
`GatewayCustomers`-ում վերագրեք `GatewayModuleId`-ն այդ id-ով։ Մինչև համապատասխան պլագին տեղադրվի,
այդ հաճախորդներին նորից կխնդրեն մուտքագրել իրենց քարտը։

### Վերբեռնված պլագիններ և ստորագրված փաթեթներ {#uploaded-plugins-and-signed-packages}

0.4.0 թողարկումը գործարկման ժամանակ ստուգում է յուրաքանչյուր պլագինի ստորագրությունը։ Այս թողարկումից
առաջ վերբեռնված պլագինները ստորագրության ֆայլ (`plugin.sig`) չունեն և թարմացումից հետո արտադրական սերվերում
**բաց են թողնվում՝ API-ի մատյանում նախազգուշացմամբ**։ Դրանք վերականգնելու համար՝

- Փոխարինեք յուրաքանչյուր պլագին ստորագրված փաթեթով, **կամ**
- Ադմինի վահանակում **Հավելումներ** բաժնում միացրեք **Թույլատրել ստորագրություն չունեցող պլագիններ** կարգավորումը և
  վերագործարկեք API-ն։

API-ի մատյանը անվանում է յուրաքանչյուր բաց թողնված պլագին։ Development սերվերները չեն ազդվում։

## Թարմացում տեղադրիչով {#upgrade-with-the-installer}

**1. Թույլ տվեք տեղադրիչին վերցնել տվյալների բազայի պահուստային պատճենը, և պահուստավորեք `.env`-ը։**

Երբ `.env`-ն արդեն կա, տեղադրիչը ինչ-որ բան ներբեռնելուց կամ փոխելուց առաջ աշխատող
`hostpanel-db` կոնտեյների միջոցով դամփ է անում տվյալների բազան։ Դամփը գնում է տեղադրման
թղթապանակի `backups/`-ում՝ ֆայլով, որի անունում կան ամսաթիվը, ժամը և տարբերակը, որին այն պատկանում է,
օրինակ՝ `backups/hostpanel-20261107-101500-0.3.1.sql`։
Ֆայլը և թղթապանակը կարդացվում են միայն իրենց սեփականատիրոջ կողմից։

- Եթե դամփը ձախողվում է, դատարկ է ստացվում կամ կիսատ է (ավարտված դամփն ավարտվում է
  `-- PostgreSQL database dump complete` տողով), տեղադրիչը կանգ է առնում սխալով՝
  նախքան compose ֆայլին, `.env`-ին կամ աշխատող համակարգին դիպչելը։
- Եթե տվյալների բազայի կոնտեյները կանգնած է, բայց նրա տվյալների ծավալը կա, տեղադրիչը
  գործարկում է միայն տվյալների բազան, սպասում է, մինչև այն միացումներ ընդունի, և ապա
  վերցնում է դամփը։ Եթե տվյալների բազա դեռ չկա (առաջին տեղադրում, որը կանգ է առել մինչև գործարկվելը),
  պահուստավորելու բան չկա, և տեղադրիչը շարունակում է։ `--skip-backup`-ը բաց է թողնում դամփը և
  թողնում է տվյալները անպաշտպան. մի օգտագործեք այն տվյալներ պարունակող համակարգի վրա։
- Առանց ոչ մի աղյուսակի տվյալների բազան որպես պահուստային պատճեն չի պահվում, ուստի այն երբեք
  չի փոխարինում տվյալներ պարունակողին։
- Պահվում են ամենաթարմ 5 պահուստային պատճենը, ինչպես նաև ամենաթարմ 10 տարբերակից յուրաքանչյուրի
  ամենահին պահուստային պատճենը (տարբերակներ, որոնց ամենաթարմ պահուստային պատճենը ամենավերջինն է, ոչ թե
  տարբերակի ամենաբարձր համարով), քանի որ թարմացումից անմիջապես առաջ վերցվածը հին
  տարբերակին վերադառնալու ճանապարհն է, նույնիսկ երբ տեղադրիչը նորից գործարկեք։ Ավելի հինները ջնջվում են,
  ուստի թղթապանակը չի մեծանում յուրաքանչյուր թողարկման հետ։ Թվերը փոխեք `--keep <n>`-ով կամ
  `HOSTPANEL_BACKUP_KEEP`-ով, և `--keep-versions <n>`-ով կամ
  `HOSTPANEL_BACKUP_KEEP_VERSIONS`-ով։ Պահուստային պատճենների անունները UTC ժամանակ են օգտագործում։
- Պահեք նաև `.env`-ի պատճենը, քանի որ դամփը չի կարդացվում առանց իր
  `ENCRYPTION_KEY`-ի՝ `cp .env .env.bak`։
- Տեղադրեք `--version <x.y.z>`-ով։ Պահուստային պատճենը, որը վերցված է այն ժամանակ, երբ `IMAGE_TAG`-ը
  շարժվող `latest` է, վերադառնալու տարբերակ չունի, ուստի `--rollback`-ը մերժում է այն։

Եթե նախընտրում եք դամփը վերցնել ինքներդ կամ լրացուցիչ պատճեն պահել այլ տեղ՝

```bash
umask 077
cd /opt/hostpanel
docker compose -f docker-compose.hub.yml exec -T hostpanel-db \
  sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  > pre-upgrade-$(date +%Y-%m-%d-%H%M%S).sql
cp .env .env.bak
```

Նշեք `.env`-ից `IMAGE_TAG`-ի արժեքը։ Այն ձեզ պետք կգա հետգրման դեպքում։
Եթե `IMAGE_TAG`-ը `latest` է, նոր պատկերներ ներբեռնելուց առաջ պարզեք ճշգրիտ տարբերակը, որն օգտագործում են աշխատող կոնտեյները՝

```bash
docker image ls --format '{{.Repository}}:{{.Tag}}' | grep hostpanel
```

**2. Գործարկեք տեղադրիչը `--version`-ով՝**

```bash
curl -fsSL \
  https://raw.githubusercontent.com/innovayse/hostpanel/main/install.sh \
  | bash -s -- --version 0.4.0
```

Միշտ փոխանցեք `--version`։ Տեղադրիչը `IMAGE_TAG`-ը թարմացնում է միայն այն դեպքում, երբ տրված է `--version`
կամ `HOSTPANEL_VERSION`։ Առանց `--version`-ի գործարկելը ներբեռնում է թարմացված
compose և Caddyfile ֆայլերը, բայց թողնում է `IMAGE_TAG`-ը անփոփոխ, ուստի հին պատկերները
աշխատում են նոր համակարգի ֆայլերով։

**3. Ստուգեք ելքը**՝ `.env`-ին ավելացված նոր կարգավորումների մասին նախազգուշացումների համար, և քննարկեք դրանք։

**4. Ստուգեք թարմացումը։** Տե՛ս [Ինչ ստուգել թարմացումից հետո](#what-to-check-after-an-upgrade)։

Թարմացման վերջում տեղադրիչը տպում է իր վերցրած պահուստային պատճենի ֆայլը և հետ վերադարձող
հրամանը։ Հետ վերադառնալու համար գործարկեք տեղադրիչը `--rollback`-ով, տե՛ս
[Հետգրում տեղադրիչով](/hy/operators/rollback#roll-back-with-the-installer)։

Երբ `.env`-ն արդեն կա, տեղադրիչը՝

- Պահպանում է ձեր բոլոր առկա կարգավորումները։ Այն **չի** վերագրում `.env`-ը և նորից չի հարցնում
  դոմենի ու էլ. փոստի հարցերը։
- `IMAGE_TAG`-ը թարմացնում է `--version`-ով կամ `HOSTPANEL_VERSION`-ով տրված տարբերակին։
- Ավելացնում է ձեր տեղադրումից հետո `.env.example`-ում ներմուծված ցանկացած նոր բանալի։ Նոր գաղտնիքները
  (օրինակ՝ `SESSION_ENCRYPTION_KEY`) ստեղծվում են ավտոմատ. մյուս նոր բանալիները ստանում են
  օրինակի արժեքը, և տպվում է նախազգուշացում։ Քննարկեք դրանք։
- TLS ռեժիմը նորից կիրառում է միայն այն դեպքում, երբ փոխանցված է `--no-tls` կամ `HOSTPANEL_TLS`։

## Թարմացում ձեռքով {#upgrade-by-hand}

**1. `/opt/hostpanel/.env`-ում `IMAGE_TAG`-ը սահմանեք** թիրախային տարբերակին։ Առանց առաջատար `v`-ի՝ օգտագործեք `0.4.0`, ոչ թե `v0.4.0`՝

```bash
# e.g. IMAGE_TAG=0.4.0
```

**2. Ներբեռնեք նոր պատկերները և վերագործարկեք համակարգը՝**

```bash
cd /opt/hostpanel
docker compose -f docker-compose.hub.yml pull
docker compose -f docker-compose.hub.yml up -d
```

Docker Hub-ի պատկերների թեգերը հետևում են `<namespace>/hostpanel:<component>-<version>` օրինաչափությանը,
օրինակ՝ `innovayse/hostpanel:api-0.4.0`։ Շարժվող `latest` թեգերը
(`api-latest`, `client-latest`, `admin-latest`) միշտ ցույց են տալիս ընթացիկ թողարկումը։

## Ինչ ստուգել թարմացումից հետո {#what-to-check-after-an-upgrade}

- API-ի մատյանը գործարկման սխալներ չի ցույց տալիս՝

  ```bash
  cd /opt/hostpanel && docker compose -f docker-compose.hub.yml logs hostpanel-api
  ```

- `GET /health`-ը վերադարձնում է `200`։
- Կարող եք մուտք գործել ադմինի վահանակ։
- Թեստային հաշիվ-ապրանքագրի PDF-ը ճիշտ է ներբեռնվում։
- Պարբերական վճարումների աշխատանքները կատարվել են ըստ սպասվածի, տե՛ս [վճարումների ուղեցույցը](/hy/staff/billing)։

## Վերադարձ նախորդ տարբերակին {#go-back-to-a-previous-version}

Տե՛ս [Հետգրում](/hy/operators/rollback)։

0.4.0-ին թարմացնելուց առաջ վերցրած դամփը վերականգնվում է միայն նախորդ տարբերակի վրա։
Թարմացումը տվյալների բազայի աղյուսակները, բանալիները և ինդեքսները վերանվանում է PascalCase,
ուստի այդ դամփը վերականգնեք նախորդ պատկերների հետ միասին և երբեք՝ 0.4.0-ի վրա։
