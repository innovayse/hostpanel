# Фронтенды {#frontends}

## Поток данных панели администратора {#admin-panel-data-flow}

`admin/src/` следует строгому пути из четырёх слоёв. Ни один слой не пропускается.

```
View
  └─ store           src/stores/<area>.ts
       └─ API composable   src/composables/apis/use<Area>Api.ts
            └─ useApi
```

- **Представления (views)** описывают, что показать, и вызывают действия хранилищ. Они никогда не вызывают `useApi` напрямую и не содержат блоков `catch`.
- **Хранилища (stores)** выполняют каждый вызов API через `runAction` и отдают `error` и `fieldErrors` для чтения во view.
- **API-композабл** оборачивает каждую конечную точку в одну типизированную функцию и вызывает `useApi`.
- **`useApi`** отправляет каждый запрос с заголовком CSRF и `X-Language`.

## Поток данных клиентского портала {#client-portal-data-flow}

`client/` добавляет один слой: собственные серверные маршруты портала стоят между API-композаблом и API бэкенда.

```
Page
  └─ store
       └─ API composable
            └─ useApi
                 └─ server route   server/api/portal/**
                      └─ API
```

Порядок слоёв проверяют правила линтера и `client/scripts/check-layers.mjs`. Шаблоны страниц с серверным рендерингом лежат в `client/templates/<template>/`.

## Набор компонентов {#the-component-kit}

Оба приложения придерживаются одинаковых соглашений о компонентах:

- Никаких «сырых» HTML-элементов управления во view. Всегда используйте компонент из набора.
- У каждого поля ввода есть placeholder.
- У каждого интерактивного элемента есть атрибут `data-testid` в формате `<area>-<element>`.
- JSDoc у каждой экспортируемой функции и каждого компонента.

## Переводы {#translations}

У каждого раздела свои файлы локалей. Перед отправкой любых изменений перевода запускайте `lint:i18n`.

<Callout type="tip">
Запускайте <code>lint:i18n</code> перед отправкой переводов. Он находит отсутствующие ключи раньше, чем CI.
</Callout>

Полный процесс перевода описан в разделе [Перевод Hostpanel](/ru/developers/translating).
