# Откат {#rollback}

Как вернуться к предыдущему релизу Hostpanel, если обновление вызвало проблему.

<Callout type="warning">
Если новая версия добавила миграцию базы данных, сначала восстановите дамп, снятый до обновления: миграции назад не выполняются. Запуск старых образов на мигрированной базе данных может повредить данные.
</Callout>

## Перед откатом {#before-you-roll-back}

Проверьте, добавлял ли релиз, с которого вы откатываетесь, миграции базы данных.
Если добавлял, в рамках отката необходимо восстановить дамп, снятый до обновления.

## Откат с помощью установщика {#roll-back-with-the-installer}

Каждое обновление с помощью установщика оставляет резервную копию базы данных с именем,
включающим версию, к которой она относится (см. [Обновление](/ru/operators/upgrade)). `--rollback` берёт самую свежую копию,
версия которой отличается от `IMAGE_TAG` в `.env`. Повторный запуск установщика на
неудачной версии создаёт более новые копии этой же версии; они пропускаются, поэтому
откат по-прежнему возвращает к версии, с которой вы обновлялись. Когда установщик
удаляет старые копии, он сохраняет самую старую копию каждой из 10 самых новых версий
(`--keep-versions <n>`), чтобы она не пропала. «Самые новые» здесь означает версии,
у которых самая свежая копия появилась позже всего, а не с наибольшим номером версии:
после отката на 0.3.1 версии ранжируются по времени последнего копирования каждой из них.
Самые старые копии более ранних версий удаляются как любые другие старые копии, поэтому
папка не растёт с каждым релизом.

При повторном откате можно получить копию **более новой** версии: после возврата
с 0.4.0 на 0.3.1 самые свежие копии другой версии это копии 0.4.0. Тогда установщик
выделенным шрифтом сообщает, что это движение **вперёд**, называет обе версии и
спрашивает `Move FORWARD to <version>?`. Ответьте «нет», если хотели вернуться ещё дальше
назад, и сначала уберите более новые файлы из `backups/`.

```bash
curl -fsSL   https://raw.githubusercontent.com/innovayse/hostpanel/main/install.sh   | bash -s -- --rollback
```

Добавьте `--dir <path>`, если установка находится не в `/opt/hostpanel`. Далее установщик:

1. Показывает копию, которую будет использовать, и версию, к которой вернётся, и просит
   подтверждения. Добавьте `--yes`, чтобы подтвердить заранее в скрипте. Без терминала и без
   `--yes` он останавливается и ничего не меняет. Копия, которая пуста или не заканчивается
   строкой `-- PostgreSQL database dump complete`, отклоняется.
2. Если база данных остановлена, запускает её отдельно, ждёт, пока она начнёт принимать
   соединения, и останавливает все остальные службы из вывода `docker compose config --services`.
3. Сохраняет текущую базу данных в `backups/pre-rollback-<date>-<time>-<version>.sql`
   (UTC), чтобы сам откат можно было отменить. Если эту копию сделать не удаётся,
   установщик останавливается до замены чего-либо. База данных без таблиц копии не
   стоит, и она не сохраняется.
4. Восстанавливает копию во временную базу данных и переименовывает её на место рабочей
   базы только после того, как всё восстановление прошло успешно. Восстановление, которое
   завершилось ошибкой, например из-за повреждённого дампа, оставляет рабочую базу данных
   ровно такой, какой она была. Базу данных нельзя переименовать, пока её держит хоть одна
   сессия, а у сервера есть фоновые процессы (в первую очередь autovacuum), которые
   подключаются сами. Поэтому перед каждым переименованием завершаются сессии, держащие
   базу, и оно повторяется до 10 раз с интервалом в секунду. Если блокировка не уходит,
   рабочая база данных возвращается на место, установщик сообщает, что база оставалась занятой
   (а не что копия, возможно, повреждена), и выводит команду для повторного запуска отката,
   которую безопасно повторять. Занятой считается только отказ сервера при переименовании
   с причиной «in use». Любой другой отказ (права, заполненный диск, отсутствующая база) приводит
   к немедленной остановке: установщик выводит собственное сообщение сервера и сообщает, что рабочая
   база данных не менялась или возвращена на место; устраните причину, прежде чем
   запускать откат снова.
5. Только теперь загружает файл compose и Caddyfile старой версии, задаёт
   `IMAGE_TAG`, загружает те образы и запускает стек. Поэтому сбой на шагах с 1 по 4
   оставляет на месте текущий файл compose.
6. Удаляет старые файлы `pre-rollback-*` сверх `--keep`, кроме самого старого файла каждой версии.
   Это происходит только после успешного восстановления и никогда не затрагивает только что сделанную копию.

<Callout type="danger">
Откат безвозвратно удаляет всё, что было записано после снятия копии: заказы, платежи, тикеты и любые другие данные. Копия, сохранённая на шаге 3, единственный путь к ним.
</Callout>

Если что-то пошло не так после остановки служб, установщик выводит, в каком состоянии
находится установка, и точные команды для запуска. При неудачном восстановлении это команда
запуска и, на случай, когда база данных выглядит неверно, команда, которая вручную возвращает
файл `pre-rollback`:

```bash
cd /opt/hostpanel && docker compose -f docker-compose.hub.yml up -d
```

Каждое сообщение точно указывает, где находятся данные. Если сама подмена оборвалась на полпути,
рабочей базы данных нет: данные, которые были до отката, остаются в базе
`<name>_replaced`, восстанавливаемая копия находится в `<name>_restore` (обе внутри
контейнера базы данных, `<name>` это `POSTGRES_DB`), а файл `pre-rollback` содержит
те же данные, что и `<name>_replaced`. Установщик выводит команду, которая переименовывает
одну из них обратно на место, затем команду запуска. Пока базы данных с рабочим именем
нет, новый `--rollback` отклоняется до каких-либо изменений, потому что его первым шагом
были бы удалены оба остатка. Если в базе данных не было таблиц, копия `pre-rollback`
не создаётся, и сообщение говорит об этом, а не называет файл.

Если восстановление прервано (установщик убит или `docker compose exec` завершился ошибкой),
установщик не гадает: он читает, какие из баз `<name>`, `<name>_replaced` и
`<name>_restore` существуют сейчас, и объясняет, что это значит, например что рабочей базы
данных нет или что в ней, скорее всего, восстановленная копия, а старые данные находятся
в `<name>_replaced`. Если не удаётся прочитать даже этот список, он сообщает, что состояние
неизвестно, и выводит команду, перечисляющую базы данных.

База данных с именем `postgres` не может быть откачена установщиком: восстановление
подменяет базы, переименовывая их из служебной базы `postgres`, поэтому
`--rollback` отклоняет её до внесения изменений. Восстановите её вручную, как описано ниже в разделе
[База данных с именем postgres](#a-database-named-postgres).

Откат не отменяет всё, что могло изменить обновление. Загруженные файлы и
тома плагинов не входят в дамп базы данных и остаются как есть, а ключи,
которые более новый релиз добавил в `.env`, остаются в нём (неиспользуемые ключи
безвредны, но просмотрите их). Возвращаются только база данных, файл compose, Caddyfile и `IMAGE_TAG`.

`--rollback` нельзя сочетать с `--version`, потому что версия берётся та, что записана
вместе с копией. Копия, снятая, когда `IMAGE_TAG` был `latest`, отклоняется; восстановите её
вручную, как описано ниже. Чтобы использовать более старую копию, чем выбранная, сначала уберите
более новые файлы из `backups/` или выполните шаги вручную.

## Откат вручную {#roll-back-by-hand}

**1. Остановите контейнеры приложения** (базу данных оставьте работать):

```bash
cd /opt/hostpanel
docker compose -f docker-compose.hub.yml stop \
  hostpanel-api hostpanel-client hostpanel-admin hostpanel-caddy
```

**2. Если новый релиз добавил миграции, восстановите дамп базы данных, снятый до обновления, прежде чем запускать установщик:**

<Callout type="danger">
Восстановление дампа, снятого до обновления, безвозвратно удаляет всё, что было записано после обновления: заказы, платежи, тикеты и любые другие данные. Перед началом убедитесь, что выбран нужный файл дампа.
</Callout>

Замените `pre-upgrade-2024-01-15-103000.sql` файлом с датой, созданным на шаге 1 обновления.

```bash
cd /opt/hostpanel

# Safety dump of the current (migrated) state:
umask 077
docker compose -f docker-compose.hub.yml exec -T hostpanel-db \
  sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  > pre-rollback-$(date +%Y-%m-%d-%H%M%S).sql

# Verify the pre-upgrade dump file (a finished dump ends with the pg_dump completion line),
# then drop and restore. A damaged dump restored this way leaves the database empty,
# so keep the pre-rollback file above until the stack works:
if ! test -s pre-upgrade-2024-01-15-103000.sql || ! tail -n 5 pre-upgrade-2024-01-15-103000.sql | grep -q "^-- PostgreSQL database dump complete$"; then
  echo "Dump file is empty, cut short or missing, aborting."
else
  docker compose -f docker-compose.hub.yml exec -T hostpanel-db \
    sh -c 'dropdb -U "$POSTGRES_USER" "$POSTGRES_DB" && \
           createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'
  docker compose -f docker-compose.hub.yml exec -T hostpanel-db \
    sh -c 'psql -v ON_ERROR_STOP=1 --single-transaction \
           -U "$POSTGRES_USER" "$POSTGRES_DB"' < pre-upgrade-2024-01-15-103000.sql
fi
```

**3. Откатите файлы compose, Caddyfile и `IMAGE_TAG`** с помощью установщика:

```bash
curl -fsSL \
  https://raw.githubusercontent.com/innovayse/hostpanel/main/install.sh \
  | bash -s -- --version 1.3.2
```

Это возвращает файл compose и Caddyfile старой версии, задаёт `IMAGE_TAG`,
загружает старые образы и запускает стек. Замените `1.3.2` версией, на которую вы
откатываетесь: значением, которое вы записали на шаге 1 обновления.

**4.** Проверьте, что `GET /health` возвращает `200` и что вы можете войти в систему.

## База данных с именем postgres {#a-database-named-postgres}

`POSTGRES_DB=postgres` это служебная база данных самого сервера. Базу, к которой вы
подключены, удалить нельзя, поэтому шаги вручную выше, запускающие `dropdb` и
`createdb` для базы с именем из `POSTGRES_DB`, для неё не подходят. Для удаления и создания
подключитесь к другой базе данных и только потом загрузите дамп.
`template1` есть на каждом сервере и обычно используется для этого. Сначала остановите
контейнеры приложения (шаг 1 выше) и снимите страховочный дамп из шага 2.

```bash
cd /opt/hostpanel

# Drop and create from template1, ending any other session that holds postgres.
# Both commands run in the database container, as POSTGRES_USER.
docker compose -f docker-compose.hub.yml exec -T hostpanel-db \
  sh -c 'psql -v ON_ERROR_STOP=1 -U "$POSTGRES_USER" -d template1 \
           -c "DROP DATABASE IF EXISTS postgres WITH (FORCE)" \
           -c "CREATE DATABASE postgres"'

# Load the dump into the new postgres database.
docker compose -f docker-compose.hub.yml exec -T hostpanel-db \
  sh -c 'psql -v ON_ERROR_STOP=1 --single-transaction \
         -U "$POSTGRES_USER" -d postgres' < pre-upgrade-2024-01-15-103000.sql
```

`WITH (FORCE)` требует PostgreSQL 13 или новее. На более старом сервере сначала завершите
сессии командой `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = 'postgres' AND pid <> pg_backend_pid()`
из `template1`, затем удалите базу без `FORCE`. Повреждённый дамп оставляет новую базу данных
пустой, поэтому сначала проверьте дамп тестом с `tail` из шага 2 и храните страховочный дамп,
пока стек не заработает. Затем переходите к шагу 3.

## После отката {#after-rolling-back}

Создайте отчёт об ошибке с описанием того, что пошло не так, чтобы проблему можно было
исправить в следующем релизе. Укажите версию, с которой вы откатились, и ошибку,
которую вы увидели в журнале API:

```bash
cd /opt/hostpanel && docker compose -f docker-compose.hub.yml logs hostpanel-api
```
