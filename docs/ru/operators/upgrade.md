# Обновление {#upgrade}

Как перейти на новый релиз Hostpanel с помощью установщика или вручную через
docker compose.

## Перед обновлением {#before-you-upgrade}

<Callout type="warning">
Делайте дамп базы данных перед каждым обновлением. Миграции базы данных выполняются вперёд автоматически при каждом запуске API и назад не выполняются. Если понадобится вернуться, потребуется дамп. Установщик делает его за вас (см. <a href="#upgrade-with-the-installer">Обновление с помощью установщика</a>); при обновлении вручную нужен ваш собственный. См. <a href="/ru/operators/backup">Резервное копирование и восстановление</a>.
</Callout>

Перед обновлением прочитайте запись о новом релизе в списке изменений. Сделайте дамп
базы данных и запишите текущее значение `IMAGE_TAG` в `/opt/hostpanel/.env`. Оно
понадобится при откате.

### Проверьте дубликаты платежей через шлюз {#check-for-duplicate-gateway-payments}

Релиз 0.4.0 добавляет уникальный индекс на ссылки платежей через платёжный шлюз. Если у двух
строк платежей через шлюз совпадают способ оплаты и ссылка, миграция останавливается
и обновление завершается ошибкой. Перед обновлением запустите проверочный скрипт. Пустой
результат означает, что миграция пройдёт без проблем.

Скрипт входит в релиз 0.4.0. Он работает с базой данных 0.3.x и с базой 0.4.0,
поэтому запускайте его до обновления. Загрузите его по тегу релиза:

```bash
curl -fsSL -o /tmp/check-dup-payments.sh \
  https://raw.githubusercontent.com/innovayse/hostpanel/v0.4.0/scripts/check-duplicate-gateway-payments.sh \
  && sh /tmp/check-dup-payments.sh hostpanel-db
```

Если сначала загрузить скрипт в файл, неудачная загрузка не передаст в `sh` пустой ответ.
Первый аргумент задаёт имя контейнера базы данных (по умолчанию `hostpanel-db`).
Если ваш контейнер называется иначе, укажите другое имя.

Если у сервера нет выхода в интернет, скопируйте скрипт из репозитория
и запустите его по SSH:

```bash
ssh user@your-server 'sh -s -- hostpanel-db' < scripts/check-duplicate-gateway-payments.sh
```

Если скрипт выводит какие-либо строки, задайте каждой отдельную ссылку (или удалите
дубликат) и перед обновлением запустите скрипт ещё раз.

### База данных переименована {#the-database-is-renamed}

Релиз 0.4.0 переименовывает все таблицы, ключи, индексы и ограничения в PascalCase (столбцы
уже были такими). Миграция переименовывает их на месте и сохраняет все данные. Обновите
собственные SQL-запросы, отчёты и скрипты под новые имена. Дамп, снятый до обновления,
восстанавливается только на предыдущую версию, поэтому сохраните его для отката и не
восстанавливайте на 0.4.0.

### Настройки, которые необходимо задать {#configuration-that-must-be-set}

Релиз 0.4.0 требует эти настройки. Задайте их в `.env` до первого запуска:

- `ENCRYPTION_KEY` в каждом окружении.
- `SESSION_ENCRYPTION_KEY` для сессий клиентского приложения. Установщик генерирует его за вас.
- `EDGE_SCHEME`: схема, по которой доступны публичные хосты (`https://` или `http://`).
- Число доверенных прокси в разделе `RateLimit` (`KnownProxies`, `KnownNetworks`, `TrustedProxyCount`).
- Абсолютные записи `Cors:AllowedOrigins`, например `https://host.example.com`.

В Production API отказывается запускаться, пока в каком-либо секрете остаётся шаблонное значение.

### Сохранённые карты и платёжный плагин {#saved-cards-and-the-payment-plugin}

Релиз 0.4.0 удаляет встроенные шлюзы для карт. Их плагины пока не опубликованы,
поэтому, если вы принимаете оплату картами, оставайтесь на 0.3.1, пока не появится
плагин для карт. Без него при оформлении заказа способы оплаты картой не предлагаются.
Банковский перевод продолжает работать.

При обновлении сохраняются ссылки на клиентов с сохранёнными картами. Они переносятся на
платёжный плагин с идентификатором `stripe`, потому что только этот шлюз когда-либо их
хранил, и используются, как только будет установлен плагин с таким идентификатором. Если
ваш плагин использует другой идентификатор, перезапишите `GatewayModuleId` в
`GatewayCustomers` на него. Пока подходящий плагин не установлен, у этих клиентов
карту запрашивают заново.

### Загруженные плагины и подписанные пакеты {#uploaded-plugins-and-signed-packages}

Релиз 0.4.0 при запуске проверяет подпись каждого плагина. Плагины, загруженные до этого
релиза, не содержат файла подписи (`plugin.sig`), и после обновления на рабочем сервере
они **пропускаются с предупреждением в журнале API**. Чтобы вернуть их:

- Замените каждый плагин подписанным пакетом **или**
- Включите **Разрешить плагины без подписи** в панели администратора в разделе **Плагины** и
  перезапустите API.

Журнал API называет каждый пропущенный плагин. Серверов для разработки это не касается.

## Обновление с помощью установщика {#upgrade-with-the-installer}

**1. Пусть установщик сделает резервную копию базы данных, и сохраните `.env`.**

Если `.env` уже существует, установщик до загрузки или изменения чего-либо снимает дамп
базы данных через работающий контейнер `hostpanel-db`. Дамп сохраняется в `backups/`
в каталоге установки, в файле с именем из даты, времени и версии, к которой он относится,
например `backups/hostpanel-20261107-101500-0.3.1.sql`.
Файл и папка доступны для чтения только владельцу.

- Если дамп не удался, получился пустым или оборван (законченный дамп завершается строкой
  `-- PostgreSQL database dump complete`), установщик останавливается с ошибкой
  до того, как тронет файл compose, `.env` или работающий стек.
- Если контейнер базы данных остановлен, но его том данных существует, установщик запускает
  только базу данных, ждёт, пока она начнёт принимать соединения, и затем снимает дамп.
  Если базы данных ещё нет (первая установка, остановившаяся до её запуска), копировать
  нечего, и установщик продолжает работу. `--skip-backup` пропускает дамп и оставляет
  данные незащищёнными; не используйте его на стеке, где есть данные.
- База данных без единой таблицы не сохраняется как резервная копия, поэтому она никогда
  не заменяет копию, содержащую данные.
- Хранятся 5 самых свежих копий и самая старая копия каждой из 10 самых новых версий
  (версий, у которых самая свежая копия появилась позже всего, а не с наибольшим номером),
  потому что копия, снятая прямо перед обновлением, служит путём назад к старой версии, даже
  после повторного запуска установщика. Более старые удаляются, поэтому папка не растёт
  с каждым релизом. Числа меняются с помощью `--keep <n>` или
  `HOSTPANEL_BACKUP_KEEP` и `--keep-versions <n>` или
  `HOSTPANEL_BACKUP_KEEP_VERSIONS`. В именах копий используется UTC.
- Сохраните также копию `.env`, поскольку дамп нельзя прочитать без его
  `ENCRYPTION_KEY`: `cp .env .env.bak`.
- Устанавливайте с `--version <x.y.z>`. У копии, снятой, когда `IMAGE_TAG` равен
  плавающему `latest`, нет версии, к которой можно вернуться, поэтому `--rollback` её отклоняет.

Если вы хотите снять дамп сами или сохранить дополнительную копию в другом месте:

```bash
umask 077
cd /opt/hostpanel
docker compose -f docker-compose.hub.yml exec -T hostpanel-db \
  sh -c 'pg_dump -U "$POSTGRES_USER" "$POSTGRES_DB"' \
  > pre-upgrade-$(date +%Y-%m-%d-%H%M%S).sql
cp .env .env.bak
```

Запишите значение `IMAGE_TAG` из `.env`. Оно понадобится при откате.
Если `IMAGE_TAG` равен `latest`, до загрузки новых образов выясните точную версию, которую используют работающие контейнеры:

```bash
docker image ls --format '{{.Repository}}:{{.Tag}}' | grep hostpanel
```

**2. Запустите установщик с `--version`:**

```bash
curl -fsSL \
  https://raw.githubusercontent.com/innovayse/hostpanel/main/install.sh \
  | bash -s -- --version 0.4.0
```

Всегда передавайте `--version`. Установщик обновляет `IMAGE_TAG` только тогда, когда указан
`--version` или `HOSTPANEL_VERSION`. Запуск без `--version` загружает обновлённые
файлы compose и Caddyfile, но оставляет `IMAGE_TAG` прежним, так что со
новыми файлами стека работают старые образы.

**3. Проверьте вывод** на предупреждения о новых настройках, добавленных в `.env`, и просмотрите их.

**4. Проверьте обновление.** См. [Что проверить после обновления](#what-to-check-after-an-upgrade).

По окончании обновления установщик выводит файл копии, который он снял, и команду
для возврата. Чтобы вернуться, запустите установщик с `--rollback`, см.
[Откат с помощью установщика](/ru/operators/rollback#roll-back-with-the-installer).

Если `.env` уже существует, установщик:

- Сохраняет все ваши настройки. Он **не** перезаписывает `.env` и не задаёт заново
  вопросы о домене и почте.
- Обновляет `IMAGE_TAG` до версии, указанной через `--version` или `HOSTPANEL_VERSION`.
- Добавляет новые ключи, появившиеся в `.env.example` с момента вашей установки. Новые секреты
  (например, `SESSION_ENCRYPTION_KEY`) создаются автоматически; остальные новые ключи получают
  значение из примера, и выводится предупреждение. Просмотрите их.
- Заново применяет режим TLS, только если передан `--no-tls` или `HOSTPANEL_TLS`.

## Обновление вручную {#upgrade-by-hand}

**1. Задайте `IMAGE_TAG` в `/opt/hostpanel/.env`** равным целевой версии. Без ведущей `v`: пишите `0.4.0`, а не `v0.4.0`:

```bash
# e.g. IMAGE_TAG=0.4.0
```

**2. Загрузите новые образы и перезапустите стек:**

```bash
cd /opt/hostpanel
docker compose -f docker-compose.hub.yml pull
docker compose -f docker-compose.hub.yml up -d
```

Теги образов в Docker Hub имеют вид `<namespace>/hostpanel:<component>-<version>`,
например `innovayse/hostpanel:api-0.4.0`. Плавающие теги `latest`
(`api-latest`, `client-latest`, `admin-latest`) всегда указывают на текущий релиз.

## Что проверить после обновления {#what-to-check-after-an-upgrade}

- В журнале API нет ошибок запуска:

  ```bash
  cd /opt/hostpanel && docker compose -f docker-compose.hub.yml logs hostpanel-api
  ```

- `GET /health` возвращает `200`.
- Вы можете войти в панель администратора.
- Тестовый PDF счёта скачивается без ошибок.
- Регулярные задания биллинга выполнились как ожидалось, см. [руководство по биллингу](/ru/staff/billing).

## Возврат к предыдущей версии {#go-back-to-a-previous-version}

См. [Откат](/ru/operators/rollback).

Дамп, снятый до обновления до 0.4.0, восстанавливается только на предыдущую версию.
При обновлении таблицы, ключи и индексы базы данных переименовываются в PascalCase,
поэтому восстанавливайте такой дамп вместе с предыдущими образами и никогда не на 0.4.0.
